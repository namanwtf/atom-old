# Technical Implementation

The module installs targeted hooks by process and functional domain. The entry point is responsible only for lifecycle, process filtering, configuration injection, and install-result aggregation; specific target location and interception logic stay within their own functional domains.

## Hook Installation and Diagnostics

- Each functional domain registers hooks through `HookRegistrar`, using stable IDs, the `PROTECTIVE` exception mode, and a unified priority policy.
- Install results distinguish `INSTALLED`, `MISSING`, `FAILED`, and `SKIPPED`, and keep the `HookHandle` to help locate signature drift after a ROM or target-app upgrade.
- Missing ordinary targets and reflection exceptions are surfaced per functional domain as failures; framework-level `Error`s such as `HookFailedError` are not swallowed by the ordinary exception-isolation layer.
- `ModuleMain` filters out irrelevant processes as early as possible and calls `detach()`, avoiding keeping lifecycle callbacks in processes that do not need them.
- Obfuscated targets for two-finger screen search are located at install time through DexKit's strings, signatures, and call relationships; interfaces with sufficiently unique signatures use structural reflection. With zero candidates or multiple candidates it abandons the takeover rather than picking the first result. The descriptor cache is invalidated when the APK's DEX checksum or the query-rule version changes, and reflection signatures are still verified after a cache hit; the resolution bridge is closed when installation ends, and runtime callbacks do not scan the DEX.
- The DexKit native library first uses the framework's standard loading and the module install directory; when both are unavailable, it extracts a native library matching the current process bitness from the module APK into the host's private cache. The cache is isolated by the SHA-256 of the library content, verified against the APK bytes before reuse, set read-only after writing, and atomically replaced. The library is always loaded by the module ClassLoader, compatible with compressed packaging; logs report native-library load and JNI-init failures separately without recording file paths from linker messages.

## Logging and Release Stripping

Atom uses one set of four-level log semantics and selects a backend by runtime environment: the app and Agent Runtime write to logcat via `AndroidAgentLogger`, and hook processes write to the Xposed log via `ModuleLogger`. Business code must not call `android.util.Log` or `XposedModule.log` directly.

| Level | Usage | Release |
| --- | --- | --- |
| `DEBUG` | High-frequency normal flows, target matching, retry details, sizes and counts | Fully stripped |
| `INFO` | Low-frequency lifecycle, hook install summaries, structured summaries of privileged actions | Kept |
| `WARN` | Recoverable degradation, fallback, target signature drift, retry exhaustion | Kept; high-frequency events must be throttled |
| `ERROR` | A request or feature that definitely cannot complete, a critical invariant violated | Kept |

Cancellation, feature-off, and missing optional targets are not logged as `ERROR`. `debug` only accepts a lazy supplier; the supplier must be pure observation code and must not perform hooks, reflective writes, state changes, or other business side effects, because Release's R8 removes the entire call.

At every level it is forbidden to log prompts, request or response bodies, API keys, auth headers, cookies, tool parameters and results, raw commands, stdout/stderr, URIs, file paths, image content, app manifests, and raw run identifiers. Exceptions by default only record their type without concatenating `Throwable.message`; externally or model-generated names must first be converted into a safe token constrained by length and character set. Only framework or reflection exceptions confirmed to carry no user data may include a full stack trace.

Release stripping treats `app/proguard-rules.pro` as the single executable source of truth, with the following rule boundaries:

- `-maximumremovedandroidloglevel 3 class io.github.namanwtf.atom.** { *; }` strips only Android `VERBOSE/DEBUG` in Atom's own code and does not affect dependency libraries.
- Precise `-assumenosideeffects` rules are used for `AgentLogger.debug(Function0)`, `AndroidAgentLogger.debug(Function0)`, and `ModuleLogger.debug(Function0)`, covering the Xposed logging backend that R8 cannot recognize.
- No side-effect-free declarations are made for `INFO/WARN/ERROR`, and no wildcard stripping rules for `*Logger` or the global `android.util.Log` are used.
- After each rule change, build both Debug and Release and check the R8 configuration/usage, DEX log calls, representative log strings, and Xposed entry metadata.

The above policy follows Android's official [R8 additional rules](https://developer.android.com/topic/performance/app-optimization/additional-rule-types), [log information disclosure prevention](https://developer.android.com/privacy-and-security/risks/log-info-disclosure), the AOSP [log level conventions](https://source.android.com/docs/core/tests/debug/understanding-logging), OWASP [runtime logging tests](https://mas.owasp.org/MASTG/tests/android/MASVS-STORAGE/MASTG-TEST-0203/), and [CWE-532](https://cwe.mitre.org/data/definitions/532.html).

## Atom Native Digital Assistant

The Manifest registers a `VoiceInteractionService`, a `VoiceInteractionSessionService` in the same process as the overlay, a full-screen `TYPE_APPLICATION_OVERLAY` assistant overlay, and a `RecognitionService` required for Android assistant-role eligibility. The settings page shows the current default digital assistant in a single row (`Atom`, another default-assistant app, or unset), and tapping it directly opens the system digital-assistant picker for the user to switch; the overlay uses the granted microphone permission, and when not granted it provides an app-permission-settings entry while keeping keyboard input.

`VoiceInteractionSession` receives the system entry and the system-provided Assist data and closes its own UI; `EtaAssistantOverlayService` holds the full-screen window, the voice-sequence animation, voice input, and keyboard input. The window draws behind the status bar, navigation bar, and display cutout via `setFitInsetsTypes(0)`, and interactive content stays reachable through status-bar, navigation-bar, and IME Insets, avoiding truncating the edge-to-edge background after adding Insets to the root container. User-submitted text is handed to `AgentRuntimeClient`; requests, streaming results, foreground tool collapse, cancellation, and archiving reuse the existing Runtime protocol. Before a foreground tool runs, Atom's own entry removes the window on the main thread and tells the system session to `hide()`, and the Runtime waits until that View actually detaches before continuing; external assistant entries still use a return action and target-package window confirmation. If microphone permission is granted and recognition is enabled at wake-up, one cloud recognition is started and the final recognition result is submitted directly; the streaming preview only appears in the input area. On failure it prompts with the reason—credentials, network, service, or microphone—and provides a voice-settings entry and keyboard input. Switching the keyboard, closing, waking again, and foreground-tool collapse all terminate recording and quarantine late results.

The `:voice` and `:recognition` processes only initialize local preferences, without warming up the database, Skills, or Xposed UI services. `RecognitionService` only keeps the declaration required for Android digital-assistant-role eligibility and is not called by the current overlay; HyperOS key adaptation is outside the current implementation scope.

Assistant context is requested via `SHOW_WITH_ASSIST` and `SHOW_WITH_SCREENSHOT`; Android 17 additionally requests structured screen content and declares the corresponding permissions and service XML attributes. The Session and the overlay share a single wake object in the main process, and the Intent carries only the association ID; a new wake replaces the old object, and the context is released after the window is closed or the system session is hidden, so late async results are not written back to the new entry. Screenshots and app text are handled independently; on submission it waits at most for the remaining two-second capture window, and the missing part does not block ordinary questions. Follow-up questions within the same overlay reuse that wake's snapshot and clearly mark the capture time; after a foreground tool changes the UI, the old snapshot is not treated as the live screen.

App content is limited by visible windows, node count, depth, and text capacity, and password-input nodes are skipped; truncation carries a marker. Screen body text enters the Runtime as an independent optional field, projected only into the current model request, without rewriting the user's words or writing to persistent context or logs; screenshots continue into the Runtime through the existing file-descriptor path. When system sharing switches, protected windows, or apps that do not provide content are involved, partial data or empty results are allowed, and GUI operations themselves still follow the accessibility tool's capability requirements.

Model screenshots for GUI, Root, the digital assistant, and the built-in browser keep their original size and pixels. Already-encoded screenshots upload their raw bytes directly; a Bitmap is encoded to PNG once on the capture side, with no re-transcoding in the Runtime. The browser only draws the viewport on the main thread, and encoding happens on the execution thread. The small preview on chat cards is generated separately and does not participate in model input; ordinary attachments and file images continue to use JPEG-compatible encoding.

## system_server

- **Power-key takeover**: Hooks `PhoneWindowManagerExtImpl$OplusSpeechHandler.handleMessage()` to handle the wake message the system dispatches to the default assistant (`what == 0x3F3`). When the target is the system default assistant it runs the original method directly; only when the target is Gemini or Atom does it intercept and dispatch to the corresponding entry.
- **Compatibility config**: The three-state target is written to a string key; when the key is absent or its value is invalid, it reads the old `POWER_KEY_TAKEOVER` boolean protocol, where `true` still means Gemini and `false` means the system default assistant. Fresh installs default to the system default, and existing users are not re-targeted because of the newly added Atom.
- **Digital-assistant config repair**: With the independent auto-set switch on, at boot, unlock, user switch, settings-page target change, and startup-failure recovery, it serially corrects the current Gemini/Atom target's `android.app.role.ASSISTANT` and secure settings via `AssistantManager`. When switching a managed target it first writes the target component's secure settings directly so the system `SettingsObserver` completes the service switch immediately (no longer clearing first or double-forcing a rebuild), then fills in `RoleManager` asynchronously; concurrent switches are merged as latest-wins through `AssistantConfigurationCoordinator`, avoiding losing the last change during rapid switching. System-default mode clears the managed binding, and no system config is written when the switch is off; verification caches and async callbacks both re-check the user and target, so an old target's task does not keep overriding a new choice.
- **Wake logic optimization**: Gemini restores the original `VoiceInteractionManagerService`, `ACTION_ASSIST`, `ACTION_VOICE_COMMAND` order; Atom first uses the active `voiceinteraction` session, then tries the same-package `ACTION_ASSIST` bridge when already configured as the default assistant (during the service-binding window `EtaVoiceAssistActivity` falls back to directly raising the overlay). When all paths fail it immediately runs the original system logic without blocking the system callback.
- **Circle to Search support**: Force-enables `ContextualSearchManagerService`, points the package name at Google App, and permits `SystemUI` and ColorDirectService call permissions. As a low-level dependency of Circle to Search it always runs and cannot be turned off.
- **Accessibility protection**: Reuses the verified `SystemServer.startOtherServices(TimingsTraceAndSlog)` lifecycle point and attaches event-driven protection after system services finish starting. Background work reuses Android's `BackgroundThread`, with no module threads and no polling; the switch is off by default, and an enable request must pass signature permission, real sender UID, service declaration, and APK signer pinning checks simultaneously. Protection only maintains Atom's component and the master switch in the owner user, and keeps other services; on disconnection it confirms via a health Provider callable only by the `system` UID, and performs targeted rebinding of Atom with a count cap and cooldown.

## Accessibility Protection

Accessibility protection verifies control broadcasts using the real sender UID provided by the system.

"Force keep accessibility" is off by default. When enabled, the protection backend injected into `system_server` verifies Atom's service declaration, calling UID, and APK signature, and corrects configuration when the accessibility-service list, the master switch, the Atom package, or the owner-user unlock state changes. It keeps other accessibility services, does not depend on app autostart, and performs no periodic polling.

If a service is still in the enabled list but has no real connection, the protection backend restarts only Atom itself, retrying at most three steps progressively; after persistent failure it cools down for one minute. When ColorOS keeps deleting the setting, the write-back interval backs off from 300 ms to 30 seconds, recovering after one minute of stability. Turning off the switch only stops protection; it does not turn off the current service on the user's behalf.

GUI tools still confirm a real service connection before executing. When protection is off, the system scope has not taken effect, or rebinding times out, the action fails explicitly rather than quietly modifying accessibility settings via Root or Shell.

If the app's control entry is unavailable, you can use ADB to stop protection and then disable the service from system settings:

```bash
adb shell settings put global eta_accessibility_protection_enabled 0
```

Deleting that setting restores the default off state. During development, after deliberately changing the signature and confirming the APK source is trusted, also clear the old signer pinning value:

```bash
adb shell settings delete global eta_app_signer_sha256
```

Intercepts the OPPO OCR screen search triggered by a long press on the bottom gesture handle, and directly calls the `contextual_search` service via binder to trigger Circle to Search.

## ColorDirectService

In `com.coloros.directui.ui.CollectInfoActivity`, it locates the screen-search entry by the `Intent → void` signature and an input diagnostic string, without relying on obfuscated method names. It reads `fingerTrigger` from `startInfo.directExt` and `touchInfo.fingerCount`, and after confirming a two-finger screen search, directly calls the `contextual_search` service to trigger Circle to Search and closes the system screen-search page; it only falls back to the original logic when the call fails.

## Xiaobu Memory

ColorOS system memory lives in the `ai_memory` database of `com.oplus.aimemory`. Atom only keeps the module lifecycle in Xiaobu Memory's default process and hooks its `DataShareProvider.call(String, String, Bundle)` to install an internal query bridge. The Runtime calls that Provider through Root with a fixed method, and the hook runs a fixed read-only query inside the target process that owns the database permission. Non-Atom methods pass through into Xiaobu Memory's own logic; the internal method only accepts UID 0, and after verification queries as the host identity without exposing arbitrary URIs, table names, or SQL to the model.

When ColorOS 17's Xiaobu Memory uses an encrypted database, Atom first verifies known Room database types and, per type, obtains the unique static singleton field and the existing connection field; only when a known type no longer matches does it re-locate through DexKit's database-factory signatures. As a result, memory queries for currently known versions do not depend on successful DexKit native-library loading. Atom does not call the factory to create databases, does not extract keys, and does not close connections held by the host. When uninitialized, it prompts the user to open Xiaobu Memory and retry. Ordinary SQLite files are still opened read-only, with both connection types sharing the fixed query engine. Read exceptions and genuinely missing tables or fields are reported separately, avoiding misreporting an encrypted-read failure as an unsupported table structure.

The query protocol only allows three operations—system memory, personal orders, and saved places—and both request and result have UTF-8 byte caps. The database layer only queries predefined tables and fields, quoting SQLite identifiers uniformly to be compatible with fields like `shipments.order` that collide with SQL reserved words. Results continue to be treated as sensitive tools and are not written to persistent sessions.

Only when the in-process query bridge is unavailable does the Runtime fall back to the Root snapshot path: it copies the main database and any WAL, SHM, or journal sidecar files, size-bounded, into Atom's cache, opens them read-only with the same query engine, and deletes them immediately after the query ends. When the snapshot is not an ordinary SQLite format, it explicitly prompts that the Xiaobu Memory hook is required, and does not attempt to read an encrypted file as an ordinary database.

## Google App

It spoofs the device as a Samsung S24 Ultra so Google enables Circle to Search, while intercepting key queries of `SystemProperties` and `PackageManager.hasSystemFeature()` so Google App sees `ro.opa.eligible_device=true`, `GOOGLE_BUILD`, and `GOOGLE_EXPERIENCE`. This corresponds to the OPA eligibility approach commonly used by ready-made Google App Magisk modules and OpenGApps, but is limited to the Google App process and does not modify system files. Device spoofing and eligibility patching always run as a low-level dependency of Circle to Search and cannot be turned off.

The device-model field is written by reflection first; when Android rejects writing a static final field, it uses the static-field interface of `jdk.internal.misc.Unsafe` and reads back to verify, compatible with Android 17's field-write protection.

Gestures are handled by the common container, preserving Compose child scroll and selection arbitration. The search capsule and the permissions and settings buttons at the bottom of the sidebar float above the scrollable list (Miuix uses `glassPanel`, `GlassIconButton`, and fade/progressive blur; COUI uses fluid material or a degraded overlay). Sidebar back is consumed only by the already-restored current home page and can also close when half-expanded; drag end and every back or tap-to-collapse directly end the system-gesture haptic, with no filtering by direction, endpoint change, or repeated back, and no custom vibration waveform. The settings page and standard secondary pages share an adaptive Scaffold: phones show a collapsible large title, and wide screens switch to a small title with content constrained to a centered maximum width. Wide-screen layout is decided by the display density and window width provided by Android.

Cards uniformly use `Card` and its default continuous corner radius; interaction feedback, theme colors, and per-page content spacing are managed uniformly by the respective design systems and page templates.

Settings and management pages share state and business actions between the COUI and Miuix implementations: the Miuix side uses `MiuixScaffoldPage` / `MiuixScaffold`, `GlassTopAppBar`, Miuix `miuix-preference`, and `miuix-glass` overlays and components; the COUI side uses `CouiScaffoldPage` / `CouiLazyScaffoldPage`, `CouiPreference`, and COUI overlays. See [Settings and Management Components](UI_COMPONENTS.md) for the specific component choices, grouping rules, and slot contracts.

Appearance configuration is saved in the existing `eta_settings` DataStore. The theme root resolves follow-system, light, and dark for both styles, and syncs the system bars and Markdown's Material color bridging. COUI uses the library's native palette, and Miuix supports the Monet color style (including `CMF`), accent colors, and a pure-black background. The Miuix top bar directly uses the OS4 `GlassTopAppBar` progressive blur (`progressiveBlur = true`) when the device supports `RuntimeShader`, and falls back to a solid background otherwise; the chat input capsule floats above the message flow under Miuix using `glassPanel` with a continuous vertical fade at the bottom. The Miuix chat top bar has a fixed height, and chat content does not join the shell's collapsible top-bar scroll connection; bidirectional scrolling is handled by the message list. Page scrolling keeps Miuix overscroll rebound and edge haptic feedback, and the landscape safe area is constrained by both the display cutout and navigation-bar Insets.

- **Atom Runtime configuration**: Default thinking, web browsing, device direct access, sensitive-info reading, sensitive device operations, and terminal/file tools are saved in app private configuration, independent of LSPosed. The Runtime reads current values at request start and before each tool execution; upgrades compatibly migrate existing RemotePreferences values.
- **Hook configuration**: `EtaApp` registers `XposedServiceHelper` in `Application.onCreate`; the framework pushes a binder through `XposedProvider` and then the `XposedService` is obtained. Hook switches such as system-assistant takeover and Circle to Search are written to the LSPosed database via `XposedService.getRemotePreferences()`; these switches stay unmodifiable while the service is disconnected.
- **Hook process**: `ModuleMain.onModuleLoaded` calls `XposedInterface.getRemotePreferences()` to cache a read-only `SharedPreferences` into `Prefs`. Each hook's interception callback entry directly reads `Prefs.isEnabled(key)`, following original logic when off; therefore in normal use, the next relevant trigger after a config change appears to apply live. This live apply comes from the hook entry reading the current config, not the libxposed API 102 hot-reload feature.
- **Delayed-task recheck**: A queued background default-assistant repair task re-checks the corresponding switch and target before executing, avoiding an old task bypassing the user's switch-off or target change while it was queued.

Non-disableable low-level dependencies (ContextualSearch service patching, device spoofing, eligibility patching) always run and expose no switch.

## Direct Personal Data Access

Personal data retrieval reuses the "Sensitive device info reading" switch; the model can read raw results when called, but tool parameters and results are not persisted into conversation records. Each capability is pinned to a verified Provider, projection fields, and sort order, accepting only length-limited keywords and result counts, without exposing arbitrary URIs, table names, or SQL to the model.

The Runtime prompt requires the model to proactively call the exposed read-only tools when the user's goal clearly benefits from on-device context. For broad tasks such as "know me", recent activity, habit and preference, and personalized suggestions, the model should sample from multiple relevant sources by time and representativeness before summarizing; a tool being exposed means the corresponding capability has already been enabled by the user, so it should not repeatedly ask for authorization or stop just because a single source is empty. When a dedicated tool does not exist, results are insufficient, or a data source is unavailable, if Root Shell, file, or terminal tools are exposed, the model continues to locate and read-only-inspect the relevant app private files and databases, first identifying the format and schema, then running bounded queries, without modifying source data.

- Standard Android Providers: gallery images, audio, shared files, calendar, contacts, call history, SMS, and download records.
- ColorOS data sources: reads note text, to-dos, ordinary recordings, call recordings, and recording summaries through fixed Providers; system memory is queried first through the read-only hook bridge inside the Xiaobu Memory process, then falls back to a Root temporary snapshot including SQLite sidecar files when the bridge is unavailable. Both paths share the fixed query engine and can search memory text and its bills, schedules, pickup codes, deliveries, places, and attachments.
- Personal context: location reads the most recent system location on demand; app activity and usage duration depend on user-granted usage access; alarms, timers, IME clipboard history, and Health Connect aggregates are queried through fixed database read-only snapshots. Health tools only return summaries for the specified time window, not raw measurement series.
- Notification history: it does not fabricate old records when the system itself has no usable history. After the user grants notification access, Atom saves title, body, source package, and time into an independent on-device database from the authorization point, keeping 7 days and at most 1000 entries; query results are still removed from persistent sessions per the sensitive-tool rules.
- Personal orders: it first retrieves the delivery, shopping, express, ticket, and travel information already recognized in system memory. A third-party app's exported IPC Provider is not an order-query contract, and Atom does not depend on its volatile private order database.
- QQ and WeChat dedicated directories: only scans verified chat-image cache directories, returning bounded file metadata by recent modification time; it does not scan videos, message databases, message text, or arbitrary other app private directories.
- When the corresponding app is missing on the device or the Provider contract changes, tools return a structured unavailable error; they do not guess data by traversing other apps' private directories.

## File Vision

`read_image` is a general file-vision capability exposed with the "Terminal/file tools" switch and does not depend on direct personal data access. It accepts any local absolute path, file URI, or system gallery URI that the user or another tool has explicitly provided; local paths are read by Root. Root copies a single, size-limited file into Atom's temporary cache, and symbolic links are read by their actual target; before sending to the model it is encoded to JPEG at original size, and the original file is never modified. The temporary file is deleted immediately after the current turn ends. The QQ/WeChat search tools are only responsible for providing image paths that can be passed in.

The runtime prompt and tool descriptions together require the model to call `read_image` at most once per turn. When multiple images need viewing, the model must consume the current image's visual result first, then read the next one in the following turn, to avoid carrying multiple tool images in one request and causing some OpenAI-compatible services to hang.

## Built-in Browser

`browser_use` is an agent browser running inside Atom, with each session holding an independent off-screen WebView while login cookies and site storage are shared. It can load JavaScript pages, extract body text preserving heading/paragraph/list/link structure, find and operate on page elements, submit forms, scroll, and screenshot without taking the foreground; when the user wants to watch the process, the session's WebView can be mounted in the app for takeover, pausing only that page's agent operations. Pages and previews are bound by the same session identity; a partial reset does not clear other pages' data, and global clearing is triggered by the explicit "Clear all browser data" action. Opening external links is still handled by the independent `open_uri` tool, which participates in phone GUI-control arbitration.

Browser screenshots and chat previews are drawn with a Bitmap Canvas without changing the shared WebView's layer type; foreground mounting uses the default layer and follows window hardware acceleration. The browser uses a same-process, non-exported, independent Activity as its host, opening and exiting with Android's default window transition, and the WebView does not participate in the app's in-app full-page corner-radius clipping; mounting and release are managed by the AndroidView factory/onRelease pair, without pausing the page or additionally switching the parent container layer.

The top keeps only the capsule address bar, page back/forward, and menu, without an overlaid title bar. The address bar supports search or entering a URL: explicit URLs, domains, and local-service addresses open directly, and the remaining text is treated as a Google search term; this only affects user input and does not change the agent navigation tool's URL contract. With no page history, the left back button exits the browser, and system back always closes the browser window. When the address bar gains or loses focus it keeps smooth expand/collapse and the submit arrow's fade-slide, with the toolbar height fixed. External open and data operations are folded into the menu; the page shows the WebView directly, with no progress bar, loading placeholder, or error overlay added. Loading state is driven by the start, end, or failure of main-page navigation, and progress callbacks do not re-enable the loading state. Operation failures give a brief toast, and the address bar can refresh to retry. Non-edit-state load-control buttons sit to the right outside the address box and to the left of the "More" menu: loading can be stopped, and refresh is available after it ends; the two icons cross-fade within a fixed area without changing the address-bar layout. Closing the current page runs directly, while clearing all browser data still requires confirmation.

Atom performs no additional URL, DNS, IP, host-count, request-method, redirect, or Service Worker interception on browser requests; pages are handed directly to the system WebView to load. The browser allows local content, mixed content, third-party cookies, automatic media playback, and form submission; the system WebView and the Android platform's own protocol support, TLS verification, and permission behavior are unchanged. Web tools can be turned off in settings.

## Terminal and Files

With user authorization it executes `user` or `root` shell commands to read/write files, list directories, run scripts, check logs, and change configuration. Session-style shells keep cwd and environment variables, async tasks run in the background, and output is read in segments. Terminal tool cards in chat can be expanded to view and copy the actual full command executed; run logs still record only controlled summaries such as length, not the command text.

Long-lived background services (listening ports, web panels, scheduled tasks, etc.) are managed through the terminal's `daemon_start`: the process detaches from the command session's process group via setsid, output is written to a workspace log file, and the task record is persisted, so it is not reclaimed when the run, session, or page ends. After an app restart, surviving processes are claimed and verified by PID and ownership markers; `daemon_list`, `daemon_logs`, and `daemon_stop` are used to view status, read logs, and stop tasks, and users can also manage them in the terminal page's task panel. Daemon task count and single log reads have caps; all tasks become invalid after a device reboot.

The terminal is divided into three environments by purpose:

- `android` is the native Android Shell, handling system, app, log, Magisk, and device-file operations. Root sessions auto-discover the BusyBox provided by Magisk, KernelSU, or APatch, and use standalone `ash` to fill in applets missing from the system PATH. The interactive console is an exception: BusyBox 1.35–1.36's ash prints a new prompt line when it receives a window-size-change signal at the prompt, so on those versions the console switches to the system `sh` and appends the BusyBox applet link (`/data/local/tmp/atom/.busybox`) to the end of PATH.
- The Linux userspace is a choice of Alpine musl or Debian Trixie glibc, persisted and shared by model tools, the block terminal, and the console; the model-visible protocol is uniformly `environment=linux`. The base rootfs and base tools are installed in separate steps; the base tool set does not include Python or Node.js. The Python profile only installs uv, which then globally installs the latest stable Python; the Node.js profile installs the latest stable currently available. SSH uses the distribution's latest stable package, and APK analysis can be installed separately in both distributions. The app side only reads the completion marker written by the installer, no longer re-checking symlinks, binaries, or execute permissions inside the rootfs from a non-Root process. Atom runs the selected environment through an independent mount namespace + Root chroot; Linux defaults to executing in `/workspace`, which maps to Atom's Android working directory, with shared storage at `/sdcard`. It is not a security sandbox and does not replace the Android environment.
- Under mainland-China networks, Alpine APK only tries Alibaba Cloud and the official CDN; the Debian main repository only tries Tsinghua TUNA and the Debian official source, with security updates fixed to the Debian official source. Successful sources are written back to the rootfs for reuse by later profile and tool installs; APT also disables HTTP pipelining (which easily triggers connection resets) and enables retries. GitHub artifacts only try one fixed HTTPS download entry before returning to the official URL, and all rootfs/artifacts must still pass fixed-size and SHA-256 verification.

The "Open terminal" entry in the home overflow menu is the terminal for manual user operation. When the bundled PTY component is executable it defaults to console mode, otherwise it uses the block terminal; the status bar can switch between the two. The console uses `libeta_pty.so` to allocate a pseudo-terminal for the shell, shared by Root and ordinary identities, with TERM declared as xterm-256color; stdin distinguishes terminal bytes and window size by frame, the grid syncs its size after portrait/landscape and soft-keyboard changes settle, and programs redraw after receiving SIGWINCH. The output byte stream is maintained by the VT-subset screen buffer as a character grid: it supports SGR colors and styles (including reverse video), cursor positioning, line/screen erase, scroll regions, REP, the alternate screen, the DEC line-drawing character set, and wide and combining character cell placement; UTF-8 and escape sequences arriving across chunks are continued, and OSC/DCS strings are not displayed; cursor position, device attributes, mode state, window size, and default foreground/background color (OSC 10/11, using the current theme color) queries are answered by the buffer and written back to stdin, with bounded scrollback. The screen buffer publishes version-cached immutable row snapshots to the UI, and lines rewritten in place by programs are also redrawn; size changes during session startup are only recorded and synced once after ready, without starting a new session. The grid uses the bundled JetBrains Mono and draws per cell, with glyphs fixed to their column, and fallback glyphs such as CJK centered or horizontally compressed per cell width without causing misalignment. The grid area connects directly to the IME, composing text is previewed at the cursor and sent only after commit, and backspace in an empty editor and hardware-keyboard keys are encoded per xterm; arrow keys switch CSI/SS3 according to the program's cursor-key mode, and paste is auto-wrapped when the program enables bracketed paste. The key bar provides Esc, Tab, Ctrl/Alt (tap for one-shot, long-press to lock), arrow keys with long-press repeat, Enter, Home/End, page up/down, common symbols, paste, and keyboard show/hide. Both modes support multiple concurrent sessions (up to 6 each), and the status bar's session list uniformly provides new, switch, restart, and close; switching environments and leaving the page do not reclaim live sessions, which are held by the ViewModel until manually closed or process death. Both modes' sessions explicitly load `/etc/profile` and `~/.profile` on startup, so user CLIs whose PATH was written by the installer can run directly.

The block terminal is organized by command, output, and exit code, switching only between Android and the currently selected Linux distribution. It uses an independent resident shell session not shared with agent-tool-call sessions; running commands continue in the background after leaving the page, and you can resume viewing output when you return, with background session output continuing to accumulate and visible on switch-back. ANSI SGR sequences in output are rendered as color and weight/italic/underline, `\r` is handled as line-overwrite (progress bars keep only the final state), and other control sequences are discarded; copy and log scenarios use plain text with escapes stripped. The input box stays usable while a command runs, writing content to the session's stdin—the status-line protocol merges the exit-code marker with the command into the same logical line output by the shell itself, so interactive commands (REPL, `read`, etc.) reading stdin do not consume the marker.

Shared folders present a user-selected Android directory under `/workspace/mounts/<name>` in the Linux environment, managed on the Linux tool environment page. Mounting does not do Android-global persistent bind mounts: each Linux session binds the source directories one by one per the current config when its own mount namespace is created, and they are reclaimed with the namespace when the session ends, so config changes take effect for the next command or a new session, and there are no residual mounts to clean up after a device reboot. Source paths and mount names go through normalization and forbidden-zone checks (system-critical trees, the workspace, and the rootfs itself cannot be sources); emulated storage such as `/sdcard` does not support changing permission bits inside Linux.

Files inside the rootfs are owned by root, and the Linux tool environment page also provides read-only file browsing: listing directories and reading files are both run on the host path through one-shot Root Shells, with paths only lexically normalized and not symlink-resolved (link targets only have Linux semantics inside the chroot); the file-preview cap is 256 KB, and files containing NUL bytes are treated as binary with no preview.

The chat input bar can reference ordinary files or folders at any local absolute path, shown separately from the original request by attachment name after sending. Atom only writes the Root-resolved canonical absolute path into the model context, without uploading, copying, or caching the original file; the model then calls file or terminal tools to read it per the task. The system file picker resolves internal-storage documents and "Recent" files that can be converted to local media-library paths; cloud drives and other sources that only have `content://` URIs do not degrade into uploads.

## Long-Term Memory

Cross-conversation long-term memory is kept in a single `MEMORY.md` in the app private directory, with no separate extraction model or background housekeeping task. The current conversation's main model calls `memory_get` and `memory_write` as needed, handling deduplication, conflict correction, and removal of stale information.

- **On-demand injection**: Each turn only auto-provides the in-budget `# Core memory`, the heading index, and the file revision; detailed sections are retrieved by the model per task, without repeatedly stuffing the whole file into context.
- **Fixed per session**: Memory sits in the system prompt, which is the start of the request prefix; every change invalidates that session's entire history in the Provider cache. Therefore the same session reuses the snapshot from the first injection: the session's own writes are already in history, so the system prompt is not rebuilt; the next turn only re-injects after memory is modified by another session or the settings page, the context is compressed, the model window changes, or a run fails. The snapshot is kept only in-process.
- **Dynamic budget**: The core injection size is computed from the current model context window; when the window is unknown it is treated as 128K, and space is always reserved for history, tools, images, and replies.
- **Atomic updates**: The file cap is 1 MiB UTF-8 bytes; the model uses revision for partial updates and must re-read on conflict; the full file is overwritten through `AtomicFile`, keeping the old content on failure.
- **User control**: The settings page can view usage, edit the full Markdown, clear, or turn off memory; turning it off does not delete the file, but the Runtime immediately stops injection and rejects new memory-tool calls.

## Per-Session Thinking Effort

Chat sessions save an independent `ReasoningEffort`; the input bar shows the actual subset of `Thinking · Off / Default / Low / Medium / High / XHigh / Max` according to the current Provider, endpoint, and model capabilities. The entry is hidden when the model does not support reasoning; a forced-reasoning model with no adjustable tier only shows a non-clickable `Thinking · Default`. After a model switch or a remote capability refresh, a saved but no-longer-valid tier is clipped down to the nearest valid tier, and returns to `Default` when there is no comparable tier.

Capability resolution uses remote exact metadata, the built-in model catalog, and Provider and model-family rules in order, then safely degrades. `Default` keeps the vendor's or an advanced custom request body's default behavior; an explicit tier is applied after request-body merging completes, so the session choice is the final override. Room, Runtime Bundle, RemotePreferences JSON, and external archives all keep the old `thinkingEnabled` boolean projection, with old `true/false` interpreted as `Default/Off`; a forced-reasoning model receiving `Off` reports a configuration error directly.

The wake state consists of an independent full-screen transparent edge-light layer and a bottom ripple layer; the portrait entry first spreads a translucent halo from the power-key height on the right edge outward, then a bright light runs quickly down the right edge and, on reaching the bottom, unfolds colored light and ripples. The halo expands fast then slowly, and continues to fade after the right-edge light band reaches the bottom. The first edge entry plays independently of the speech-recognition state, and the ripple starts at the edge-arrival time; the bottom colored light's top fades out naturally and the entry outline then disappears, avoiding a fixed-height bright background. Switching back to voice within the same overlay directly restores the bottom effect. The three suggestions enter staggered above the input area and move with the IME and input area. The keyboard state hides the listening light effect after the first entry ends and keeps the suggestions. The voice state only shows white temporary text for "Listening" or recognition-in-progress on the left. The bottom ripple uses bundled shaders, palette textures, and numeric animation tracks, drawn on the hardware canvas via Android RuntimeShader; volume is consumed only in the draw phase. On a software canvas or when effect loading fails, the ripple is skipped and a controlled error is logged, without affecting voice and text interaction. A recognition service explicitly configured by the system can be used even without a declared binding permission, while an unconfigured external service still requires the binding permission.

The overlay reply area grows continuously in one direction from its initial height with the measured content height: when the first and last entries fit on screen it smoothly pushes the target value up to the real content height, with no rebound spring and continuous velocity; when content exceeds the current target and the first/last cannot fit on screen it rises directly to the maximum height, with the list's internal continuous follow-bottom scroll taking over, without shrinking back after streaming output ends. Once the user drags or scrolls, auto-resize stops and a manual anchor decides the height; it also pauses while the keyboard is shown. Text and thinking increments reuse the chat page's 80 ms merge strategy, and block boundaries, completion, and cancellation flush pending increments first. Programmatic follow-bottom does not participate in panel dragging; the list's swipe-up expansion is kept, takeover only recognizes an over-top pull on the top handle, and scroll and inertia fling no longer mistakenly enter the body; after takeover it lands on the main chat page and selects the corresponding conversation, without opening a separate conversation page. The input area no longer stacks spring-size animation onto system IME Insets. On window removal the Composition is explicitly destroyed, stopping invisible animations.

The top handle's gesture callback updates with reply state, without breaking the drag on recomposition; the callback updates via lambda, avoiding structural-equality comparison of local function references retaining the first empty-session state. Over-top distance only accumulates the part beyond the maximum height, and reverse dragging retreats within the threshold. After the list reaches maximum height, scrolling the body continues without accumulating takeover distance; gesture cancellation only resets position, without triggering close or takeover. Takeover state is held by the overlay Service, and on launch failure or body-wait timeout it restores dragging, allowing another attempt.

The overlay renders text-plus-solid circular buttons, a light input bar, a reply card, and an independent input capsule respectively for listening, keyboard input, and an existing reply. When the input bar is focused or the keyboard rises, clearer solid background and borders are used, and voice errors are shown as a status label adjacent to the input bar. The reply card uses top rounded corners and a thin outline, user messages are collected in a small bubble on the right, thinking and tool steps are collected into an expandable status row, and answer body text keeps its Markdown streaming rendering; the card height shrinks continuously with the IME as the keyboard rises.

## UI Restoration

External launch requests only save targets not yet consumed; already-processed assistant, conversation, and settings jumps are not re-executed when the system replays the original Intent. The sidebar switch and the chat's follow-bottom state are saved with the UI, and restoring a history reading position does not proactively jump to the bottom. Saved state contains only the target identifier and a little UI state, with conversation text loaded from Room on demand; this boundary follows the [Compose state saving recommendation](https://developer.android.com/develop/ui/compose/state-saving). Lifecycle logs only record the task number, whether there is restore state, and the rebuild type, to distinguish Activity rebuild from a proactive jump.

## Chat Streaming Rendering

History messages trigger automatic prefetch on actual scroll-up, with no pagination button shown normally; a lightweight progress shows at the top while loading, and a retry entry appears after failure. New-page insertion uses stable message identifiers to keep the reading position, and does not force-cancel scrolling while a finger or inertia is still scrolling. First opening a conversation positions to the most recent message, with an existing saved position still restored first; after returning to the latest position, older large page windows are reclaimed per the saved state.

The model's SSE body and thinking increments are first merged at the app state layer every 80 ms to reduce high-frequency list-state writes; block boundaries and tool events flush pending increments first, with event order unchanged. The Markdown rendering layer is project-built (`ui/markdown/`): it serially parses the GFM syntax tree in the background, then immediately converts it into its own block model (paragraphs, headings, code, math, quotes, callout blocks, lists, tables), with blocks identified by source offset, and the builder reuses unchanged block instances by source slicing, skipping them during composition; only the tail block rebuilds text and layout. Link, bold, and inline-code styles are written into the document at build time and rebuilt wholesale on theme switch. Math formulas use the RaTeX native core library for background pre-layout into a font-size-independent vector display list with bounded caching; layout is triggered only after delimiters close, and the original text is kept both while unclosed and on parse failure. `$...$`, `$$...$$` are compatible with immediately adjacent Chinese characters and parentheses and exclude currency expressions; LaTeX's `\(...\)` and standalone-line `\[...\]` are replaced with `$$` delimiters of equal length before parsing, keeping backslashes and underscores inside formulas without changing source offsets, and code blocks, inline code, and Markdown-escaped brackets are unaffected. Inline formulas align to the host text baseline and compensate a small spacing for adjacent Chinese characters; block formulas are centered with spacing, long formulas support horizontal scrolling and edge fade, and both selection and whole-copy keep the LaTeX source with original delimiters. Any unrecognized syntax also falls back to original text, so content never silently disappears. Reference-style link definitions may appear at the end and are only parsed once in the terminal snapshot. Not-yet-started targets merge into the latest full text; when subsequent appends arrive during parsing, already-completed valid prefix snapshots are still published, avoiding high-speed output continuously starving display updates. Old snapshots no longer applicable are discarded only when upstream corrects the full text. The input field uses state-based `TextFieldState` to hold the edit buffer inside the component; per-character edits do not write back to chat page state and do not go through the legacy `CoreTextField` pipeline.

LaTeX delimiter preprocessing consumes newlines before judging fences, guaranteeing the scan cursor keeps advancing. Blank lines inside fenced code and original LF/CRLF line endings stay unchanged; content in an unclosed fence is kept as original text, and formula recognition resumes after it closes.

In-progress thinking expands with a bounded tail window, showing only the last four lines with a top fade, and auto-collapses after completion; after manual expand/collapse it no longer auto-switches, and tapping the in-progress window expands the full text. The expand state of thinking and work process is derived in the composition phase per lifecycle and lands in the same frame as body-entry insertion; during the collapse animation the tail window's height cap is kept, so the full text does not flash then collapse at the end. The work process has no card shell: collapsed it is a one-line summary (e.g. "Thought 2 times · called 8 tools"), and expanded it is a timeline with thin guide lines on the left, each node marked with a lightweight icon (only running or failed states carry a soft glow). It stays expanded while still the end of the current turn, auto-collapses when the body starts or the turn ends, and also respects manual choice; finished groups whose members are unchanged reuse the original entry to skip recomposition. Consecutive calls to the same tool merge into one node (browser entries stay separate because they carry a live preview). Collapsed tools show only a title and one conclusion line: the terminal takes the last output line, failure shows the reason, and a normal success takes no line; the command, full result, and browser preview are composed only after expanding. Tools running over 3 seconds show an approximate UI-side timer, not written to the archive. Thinking content directly shows each parsed increment, with layout and visible text updated in sync, not going through the body's character-by-character reveal queue, and not replaying backlog at the end. After foreground thinking ends, it continues receiving the final parsed snapshot and shows stable Markdown with that same result; completed thinking restored from history or the background shows the full text directly.

Markdown blank lines only participate in block-structure parsing and do not accumulate visible height by source count; stable and streaming rendering share the same block-level layout, allocating spacing by the relationships among body, headings, lists, quotes, math, code, and tables, with the first block not shifted down extra. Block spacing uses typography units scaled by the system font, enlarged before headings and moderately tightened after them, with thinking tone tightened proportionally overall, keeping a clear hierarchy at large font sizes. The Runtime also requires the final answer to use legal and restrained GFM: prefer short paragraphs for ordinary conversation, use headings, lists, and tables only when they help grouping, steps, or comparison, keep each table row independent, and avoid using a whole-sentence bold as a heading.

The body's character-by-character effect is driven by a single answer-level frame clock. Paragraphs, headings, formulas, code blocks, and table cells first complete one real layout, then `DrawModifierNode` clips the `TextLayoutResult` by grapheme and formula-atom boundaries; frame-to-frame advancement only invalidates drawing, without rebuilding the Markdown AST, `AnnotatedString`, or text layout. Reveal speed is based at 36 graphemes/second, growing with backlog without a fixed speed cap; the per-frame advancement is distributed across blocks in source order, and remaining advancement is not dropped between paragraphs, formulas, code blocks, and table cells. When inline syntax and formula closing cause rendered text to collapse, reveal progress stays monotonically advancing and does not rewind to retype shown text. The prefix path accumulates by grapheme increment, triggering one measurement and increasing text height only when reveal crosses into a new line. Emoji ZWJ sequences, skin-tone modifiers, combining diacritics, flags, surrogate pairs, and closed formulas are all shown as complete atomic steps, never split in the middle.

Follow-bottom is released only when the user actually drags, and scrolls only when the message actually grows taller and the bottom sentinel leaves the viewport; pure network-status updates do not repeatedly trigger scrolling. After the network ends, follow-bottom continues to cover parsing, text reveal, and stable-layout switching, finishing after the trailing action row completes layout and the list is scrolled to the bottom; when the user drags to view history it stops following immediately, and manual expansion of a completed message does not trigger follow-bottom. After parsing catches up and the reveal queue drains, the answer directly reuses the final Markdown snapshot consistent with the current full text and switches to a selectable static view; the link index completes with the final background parse, and switching does not restart parsing or go through a raw-text Loading placeholder, avoiding a transient jump in body layout and height. Token-usage events only update the usage field without touching the message's streaming flag, avoiding repeated streaming/static view switches at turn boundaries.

When returning to the chat page, the full text already present at restore time is used as the reveal baseline; the Markdown corresponding to that baseline finishes layout before later incremental animation starts, without guessing by fixed frame count whether parsing is done. Completed replies, thinking, and tool records show stable content directly; the work process is collapsed by default when a completed task is first opened, and the user's manual expand/collapse choice is saved with the entry. Text nodes detached from layout catch up immediately without blocking other nodes' reveal queue. The render-complete callback must correspond to the current full text and terminal state, and must not end new streaming content early from an old snapshot.

Streaming parse state is kept only while the message is still generating or the entry is still composing; ended and detached-from-composition state is released. The terminal document moves into the static cache, and scrolling back into history shows stable text directly. The static cache controls capacity by both entry and source length; over-long documents display normally but are not cached long-term; the source budget limits retention scale and is not the exact heap byte count of the parse tree. See [Android memory management recommendations](https://developer.android.com/topic/performance/memory/manage-app-memory) for memory-management boundaries.

## Power and Overhead

Aiming for minimalism, never adding extra burden to the system:

- No polling, no keeping the Google process alive, no continuous log writing.
- Accessibility protection is off by default; when on it only responds to settings, package, user lifecycle, and explicit Runtime reports, with backoff for setting contention and count-and-cooldown caps for disconnect rebinding.
- The hot path keeps only the `OplusSpeechHandler` hook actually verified effective on the current model.
- Default-assistant config checks carry a 15-second cooldown.
- High-frequency success paths use `DEBUG`; Debug builds are diagnosable, and Release is deterministically stripped by R8.
- The power-key interception path performs no sleep, polling, or blocking wait; this trigger only makes a fast launch attempt and falls back to system logic on failure.
- Default-assistant repair runs asynchronously and serially per user, concurrent switches merge as latest-wins, and role, target, and switch state are re-verified on completion.

## Model Request Caching

Providers reuse the cache by request prefix, and any single-byte prefix change re-bills everything after it. The Agent loop therefore keeps the prefix stable within a session:

- **System prompt**: Only holds session-stable facts. Root only distinguishes authorized vs. not, with detection progress and failure reasons told to the model by the `check_root` result; the system prompt is rebuilt only when authorization actually changes. Memory is fixed per session; see "Long-Term Memory".
- **Tool catalog**: Only grows within a run, never shrinks. When a capability is lost mid-run the tool stays in the catalog but is re-checked before execution under the same rules as catalog filtering, returning a corresponding error code without executing; newly enabled capabilities are appended to the end, and the whole thing is rebuilt when Root authorization changes.
- **Anthropic format**: The tool catalog, system prompt, and last message each get one `cache_control` breakpoint, with the last breakpoint moving forward each turn and skipping observation screenshots that would be removed next turn. Assistant messages in the current turn's tool loop carry their thinking-signature blocks back verbatim, while earlier turns are uniformly stripped, keeping a consistent per-turn shape.
- **Usage statistics**: Cache hits read OpenAI's `prompt_tokens_details.cached_tokens`, Anthropic's `cache_read_input_tokens`, DeepSeek's `prompt_cache_hit_tokens`, and some compatible endpoints' top-level `cached_tokens`.

## Expected Behavior

When the power-key target is Gemini, a long press restores Google's original system assistant and Activity fallback chain. When the target is Atom and Atom is already the default digital assistant, a long press opens the edge-to-edge full-screen assistant overlay and prioritizes a single voice input, switchable to the keyboard; the system captures the screenshot, foreground app, and page content at wake-up, the Session receives them asynchronously, and the overlay sends them automatically with the question, no longer showing a manual add-screen button and not depending on accessibility screenshots. After the user submits text, tool execution, streaming results, and archiving are still handled by the Agent Runtime in the main process, and speech recognition calls the Qwen or Doubao cloud interface through the unified session controller. The assistant overlay can auto-speak the final answers of voice questions; playback stops when recording starts, the window is hidden or closed, with no background catch-up speech. Chat dictation first inserts an editable draft, and historical answers can be read aloud manually. See [Voice Setup and Implementation](VOICE.md) for configuration, protocol, and lifecycle boundaries.

When Atom is not yet the default assistant and auto-set is off, it returns directly to the system default assistant per the established policy, without creating a parallel Activity session. With auto-set on, a failed trigger only repairs the current selection in the background, while the current long press still falls back immediately; subsequent triggers use the repaired main path. Going forward HyperOS only needs to connect the vendor key event to the same target-dispatch boundary, without modifying the text session or the Runtime.

The configuration UI saves switches by consumption boundary: agent and local tools write to app private configuration, and hook capabilities write to the LSPosed-side RemotePreferences. Hook callbacks and delayed tasks both read the corresponding switch before executing, so subsequent triggers run per the current configuration.
