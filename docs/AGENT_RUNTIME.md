# Agent Runtime

Atom's Agent Runtime organizes a single user input into model turns, tool execution, and a persistable incremental transcript. It runs in the module's own process; hook processes are only responsible for recognizing entries, sending requests, and receiving results.

## Code Boundaries

- `AgentModelClient`: the stable facade, configuration, and cross-process session DTOs.
- `AgentLoop`: the state machine for a single run, independent of Android Service, Room, or Compose.
- `AgentPromptBuilder`: system constraints, the Skill index, history, and the current user input.
- `AgentConversationCodec`: conversion between Provider JSON and stable session DTOs.
- `AgentToolCatalog` and its grouped catalogs: the tool schemas visible to the model, without executing tools.
- `AgentTraceFormatter`: only produces displayable, recordable redacted summaries.
- `AgentWebTools`: public web search, anonymous HTTP body reading, and paginated snapshots for the current run; does not occupy the session WebView.
- `AgentProviderClient`: the OpenAI-compatible, Anthropic, and Gemini Interactions protocol boundaries.
- `AgentRunController`: cancellation, pause, and steering queue.
- `AgentRuntimeSession`: each run holds its own reply channel and guarantees a unique final result.
- `AgentRuntimeRunExecutor`: the unified exception boundary from Skill/tool initialization through model execution, resource cleanup, and terminal-state commit.
- `AgentRuntimeService`: Android lifecycle, entry IPC, and overlay host; no longer inlines the Agent execution loop.
- `RuntimeRunRegistry`: registers prepare, execute, and commit states per run, controlling same-session writes and active-task admission.
- `GuiControlCoordinator`: exclusive control, FIFO waiting, and user takeover for the phone GUI operation phase.
- `BrowserSessionRegistry`: manages independent browser pages and their lifecycle by existing session identity.
- `AgentRunStore`: UI-side multi-run subscriptions, cancel intents, and event buffering, without deciding Runtime scheduling.
- `ShellProcessSupervisor`: admission, independent process groups, cancellation, and reclamation of Android/Alpine/Debian Shell processes; the terminal protocol does not carry process-ownership details.

## Loop Semantics

A turn is "one assistant response + the complete tool batch that response submits". The loop follows this order:

```text
pending steering
→ provider response
→ assistant history
→ tool batch (executed serially in model order)
→ contiguous tool results
→ optional image observations
→ next turn / final result
```

Key invariants:

- Steering is queued one item at a time by default and injected only after the current turn fully completes; it does not cancel the current HTTP request or close tool resources.
- All tool results in the same assistant message must be written contiguously, followed by image observations that are not supported by the Provider's native tool-result image support.
- With `finish_reason=length` or `max_tokens` and tool calls present, no possibly-truncated arguments are executed; a structured error result is written for each call so the model can re-plan.
- Only an explicit `tool_calls` / `tool_use` termination reason permits executing tools; calls smuggled into `stop`, content-filter, or unknown termination reasons are rejected as protocol contradictions.
- Tool schemas describe parameters to the model. The Loop only confirms a tool is available in this turn's catalog, passing parameters verbatim to the local executor or MCP service, without re-running JSON Schema prechecks on the client. Required parameters are read at the actual usage site, and execution failure is returned to the model as a tool result; unused extra fields do not fail the whole call.
- The transcript only returns the assistant, tool, and in-flight steering messages newly added in this run, without repeating old history or the turn's initial user message.
- Tool batches within the same run stay serial; different sessions can run in parallel. The phone foreground is additionally mutually exclusive per GUI operation phase, and terminal sessions keep their own execution order.
- A single run has no fixed turn count or total time limit; it ends by natural model completion, user cancellation, or an unrecoverable error.
- cancel is a termination signal; pause is a checkpoint block; steering is next-turn input. The three cannot simulate each other.
- The cancel main-thread path only emits cancellation and closes resource admission: the browser verifies ownership by session instance and runId; the terminal immediately closes new foreground-process admission and, in the background, terminates synchronous commands and sessions by independent process group, reclaiming their threads and streams; already-submitted background commands are managed by the app host and must be stopped separately. On Android, when `setsid` or PID/PGID ownership handshake is unavailable it fails closed; parent-child tree snapshot fallback is only allowed in non-Android test environments. A random ownership token is verified before termination to avoid killing unrelated processes after a stale PGID is reused.
- The final steering check atomically closes the admission entry; after the Loop returns, unconsumed supplementary instructions are not misreported as received. Supplementary instructions also do not release pause.
- User cancellation and normal completion compete for a unique terminal state through their respective `AgentRuntimeSession` `RUNNING → COMMITTING → TERMINAL` state machines; the commit winner exclusively owns the outbox, archive, and final publication, and clients wait for the final result or Binder disconnect rather than cancelling by wait duration. A new session's request does not replace another session's task.
- Entry requests can only shrink tool capabilities, not grant authorization on their own. The Runtime trims configuration when a run starts, re-reads user switches before each browser, terminal, and device-tool execution, and removes reasoning/thinking override fields from custom request bodies when thinking is off.
- Device tools are divided into direct-access tools, sensitive-read tools, and sensitive-action tools, all enabled by default. The Runtime re-reads user switches before each execution; once the switch allows it and parameters match the tool schema, it executes without re-matching the user's words and without maintaining a blacklist of key packages, system apps, or Settings keys.
- WeChat sending provides no dedicated tool, parameter protocol, or extra policy layer; it entirely uses generic GUI tools to observe and operate the WeChat UI.
- Raw values returned by notifications, SMS OTPs, Wi-Fi credentials, logs, and settings read/write are transient sensitive tool data. The current model turn may use the raw values, but the persistent transcript replaces the corresponding tool parameters and results simultaneously, keeping them out of the conversation database or later IPC.

The assistant entry's `assistant_screen_context` is a bounded, optional single-run field; a missing legacy entry is treated as empty content. Raw app content is kept only in temporary metadata of the current user message and projected as data text when sent to the Provider. Stable session encoding and compressed-summary input do not include that metadata, and the user's words stay unchanged. Screenshots still use the existing image-transfer protocol.

Screenshot images carry an optional `preserve_original` flag: the Runtime keeps the original bytes, encoding, and dimensions after receiving a file descriptor or inline image, without re-converting to JPEG. When the legacy entry lacks that flag, attachment-compatible encoding is still used. When the system provides only a Bitmap, it is encoded once to original-size PNG on the capture side; afterwards only the Base64 wrapping needed for transfer is performed, with no decode-redraw, scaling, or background compositing. When capacity is exceeded it returns an error rather than bypassing the cap by lowering screenshot quality.

Design basis for the tool interface: OpenAI's [Function calling](https://developers.openai.com/api/docs/guides/function-calling) emphasizes clear parameter descriptions, predictable behavior, and having the program supply information it already knows; its recommended strict mode is a model-generation-side constraint. Anthropic's [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) emphasizes unambiguous parameters and actionable error feedback. These suggestions do not equate to removing all input handling; Atom places parameter interpretation at the actual execution boundary, keeping the semantic checks required for system permissions, resource budgets, and concrete operations, without maintaining a parallel generic validator.

## Multi-Session Parallelism and GUI Control

A session holds history, and a run holds one execution. App chat, manual compression, and reply rewriting share a same-session single-write constraint; the existing queueing, steering, and stopping remain user choices. When the main chat steers a plain-text or file-reference message, it writes directly into the current active run's `AgentRunController.steer` via `MSG_STEER`, without interrupting the in-flight model request or tool batch, and appends the supplementary instruction (`_eta_steering`) at the end of the context at the next turn's safe boundary to preserve the prefix cache; only when the current run cannot accept it (e.g. compressing or already in terminal commit) or the message contains an image is it kept at the head of the queue to be emitted with priority after the current run completes. Active stop is triggered only by the stop button. The Runtime registers run and session occupancy before materializing images, does not re-execute a duplicate active run, fails explicitly when exceeding the admission cap, and centralizes limits in `RuntimeRunRegistry`. Preparing, waiting-for-GUI, paused, and committing tasks all count toward the active set, with no additional global task queue. System-assistant entries keep their own return and in-entry cancellation behavior.

GUI tools automatically acquire control before executing, keeping it across model turns and covering observation, reasoning, action, and verification. Other tasks wait in FIFO order, and waiting is cancellable; permissions are re-checked after acquiring control. The zero-argument `release_gui` ends the calling run's operation phase, and normal completion, failure, and cancellation also wind it down; control is handed to the next task only after the current underlying action exits. Acquiring control precedes foreground side effects such as closing the assistant panel, and streaming tool-name events are for display only.

After a control change or user pause, old node and coordinate observations become invalid; actions that depend on the current page must re-run `observe_screen` first. An overlay pause means the whole device is handed back to the user, pausing the holder and blocking other GUI tasks from entering; stopping that holder does not automatically resume phone operations, which must be explicitly resumed by the user. Non-GUI tasks keep running. A tool's GUI classification is declared centrally by `AgentToolRequirements`; Shell, MCP, file, and ordinary structured calls do not join this lock, nor guarantee external-side-effect isolation of arbitrary commands.

The overlay is bound to the current GUI control, and background-task events do not override it; execution notifications aggregate across all active tasks. UI selection only decides the current display object, and background continuations resolve configuration from the target session and default model. Deleting a running session first cancels, saves, and confirms the result, then deletes; if the result is incomplete or saving fails, the session is kept.

With "Background virtual-display execution" enabled and the device having Root or LSPosed `system_server` enhancement plus passing focus and IME capability checks, `launch_app` and `open_uri` default to smart canvas routing (`display=auto`): if the target app is already in the foreground of the physical main screen or belongs to the system launcher/SystemUI, it operates directly on the physical main screen, avoiding pulling away the Task the user is watching; cross-app delegation tasks instead start automatically on the trusted background virtual display, and subsequent `observe_screen`, node actions, coordinate gestures, and text input are routed to that virtual display through the current run's active canvas. The virtual display keeps its own window focus without seizing the system top focus, and the IME policy is hidden; when the device does not meet creation conditions, the main screen is used. During background virtual-display operation the physical main screen's edge light is not drawn, and an `18×32.dp` live miniature viewfinder is embedded to the right of the status capsule; tapping the capsule expands a gallery-framed window in place for live preview, direct touch takeover, or one-tap full-screen projection. When the model completes the preliminary operations on the background virtual display and reaches the payment-confirmation/QR-code/result page, it can call `present_to_user` to smoothly migrate the RootTask from the virtual display back to the physical main screen in place.

`launch_app`'s `ok=true` means the launch request has been submitted. The tool queries the target display's windows within a bounded time; `launch_status=window_observed` means the target package's window was observed, and `unconfirmed` means not yet confirmed; `window_observation` keeps the query status and actual window information. Confirmation does not require the window to seize input focus or the app to provide operable nodes. When unconfirmed, observe the canvas first rather than immediately re-launching. After a running virtual display is removed or the bridge process exits, old observations become invalid and subsequent GUI tools return `DISPLAY_UNAVAILABLE`, without quietly reusing old coordinates on the main screen.

Accessibility queries used for node observation and pre-action validation run on a bounded serial worker thread owned by the service, and window-event callbacks only update a local version and notify. Both the main screen and the virtual display select windows by display ID, and the package name, window ID, and nodes in `focus` come from the same window observation; `focused` and `active` reflect system properties separately, null when unknown, without using the most recently launched package name as the current window. `ui_tree_status` distinguishes `available`, `empty`, `no_window`, `root_unavailable`, `timeout`, `busy`, `service_unavailable`, `query_failed`, and `not_requested`. An empty tree does not mean the app does not support the virtual display; it can be judged together with the current screenshot. The system uiautomator suppresses other accessibility services, so it is used only when there is no active accessibility connection, Root is authorized, and the target is the main screen, without repeatedly starting that channel just because active services return an empty tree.

The browser creates an independent instance by app session ID or existing external-archive identity, with unbound manual browsing using an independent page. Each page's URL, DOM, preview, cancellation, and takeover do not mix, while cookies and site storage remain shared. Consecutive runs of the same session reuse pages; deletion, reset, and low-memory cleanup release idle pages, and active or mounted pages are not reclaimed. Partial page destruction does not call app-level cache or cookie clearing; global clearing is an explicit, independent user operation. Pages are kept only in-process, without automatically replaying navigation or forms.

Multi-run queries return preparing, executing, waiting-for-GUI, paused, and committing states plus session ownership; the legacy single-run query keeps a compatible projection. The app reconciles using the active set plus checkpoint and outbox; when there is no checkpoint yet during the prepare phase, it can still reconnect via the active snapshot. GUI waiting and ownership are runtime states; device control is not restored from persisted events after a process restart.

## Optional Character Context

Characters are bound by app session; the Runtime reads the character ID and a fallback snapshot from that session's persistent records, then freezes the latest card used this time. Ordinary sessions and the system-assistant entry use the default persona. Character definition, worldbook, and story memory are provided by an independent context projection, while tool rules and executors continue along the Agent chain.

A character session's real-world memory tools are read-only, and story-memory tools are implicitly bound to the current character. Worldbooks and depth notes appear only in the current model request and are not written into the execution transcript; the character compression summary keeps both fictional story and real-task facts.

`rewrite_reply` is an independent operation that uses the `REPLY_REWRITE` request purpose to disable local and managed tools and custom body overrides, and does not accept steering. It only produces body-text candidates; temporary context and synthesized rewrite instructions are not committed to the main session. Messages associate body revisions via stable identifiers, the original journal, tool results, and run archive are kept independently, and candidate commit and restore are idempotent by run ID. See [Characters](CHARACTERS.md) for detailed user boundaries.

## Provider Protocol

The Provider's default base prompt defines Atom as an AI assistant running on an Android device that can answer questions, converse with the user, and understand the device and perform operations through tools; answers use the user's language, concisely, directly, and naturally. The default body text is authoritative from `BuiltinProviders.DEFAULT_SYSTEM_PROMPT`; new built-in Providers prefill that default; after the user clears it, the default prompt is not re-added, and existing non-empty configuration keeps its value. Ordinary sessions use the system prompt filled in the Provider, and the underlying runtime rules do not force the Atom identity; after binding a character card, the character-card definition is used instead, keeping the character's identity and tone both in conversation and when performing real tasks. Leaving it empty or using a character card does not affect tool permissions, execution-result authenticity, or the real-world memory boundary.

The Runtime provides model information independently of the persona, labeling the actual value of `ModelConfig.model` as "the currently configured model", updated with this run's configuration, without using a model display name or history messages to infer the current model, or inferring deployment version, knowledge cutoff, or capability from it. General communication rules require answering daily questions directly, clarifying only when key parameters are missing, adjusting detail to the user's needs, and reporting tool-operation results truthfully; personalized analysis distinguishes facts from speculation and does not assert personality, motives, or psychological state from scattered records. System rules such as tools, memory, and Skills are still appended per runtime conditions.

OpenAI-compatible Providers can select `Chat Completions` or `Responses API` on the configuration page. The built-in OpenAI after fresh install and reset defaults to Responses; existing Providers in the database are not overwritten by defaults. Custom Providers and other built-in Providers still default to Chat Completions.

The Provider's authentication method and model protocol are saved separately. API keys keep the existing compatibility path; Codex and Grok subscriptions use an explicit connection configuration with fixed official URLs and protocols. OpenAI uses the Codex public client's PKCE authorization, with the callback listening on `127.0.0.1:1455/auth/callback`; xAI uses device-code polling. The system browser hosts authorization, and the Agent's built-in WebView does not participate in account login. Both flows support cancellation, and the callback listener closes after ending.

OAuth credentials are managed by the main process's `ProviderCredentialRepository`, encrypted with an Android Keystore key and atomically written to a non-backup directory; Provider, RemotePreferences, IPC, and backups carry only the auth method and a stable Provider identifier, not the OAuth token. External entries rebuild OAuth configuration inside the Runtime from the local Provider and model, and cannot specify the credentials' target address. Copying uses a new Provider identifier; delete, reset, and auth-method switch clear old credentials. Backup first commits imported subscription connections in a disabled, credential-less state, restores the auth method and enabled state only after old authorization is cleaned; failing before commit leaves original credentials untouched, and failing cleanup after commit reports partial success explicitly and keeps the connection disabled, requiring re-login after restore.

Model inference and remote-catalog requests obtain valid credentials before sending; concurrent refreshes for the same account run only once, refresh results are saved as a whole, and login/logout generations prevent late results from overwriting the current session. Temporary network errors keep credentials, while definite invalidation requires re-login. HTTP 401 allows one refresh only before the response stream is consumed; this recovery does not replay the model stream or tools. Subscription requests forbid redirects, and auth and model-routing headers cannot be overridden by custom request headers. Codex logout clears local tokens; Grok also attempts to revoke the remote authorization.

Codex and Grok subscriptions reuse the Responses codec, using flat function tools, `store: false`, and streaming responses, explicitly requesting `reasoning.encrypted_content` and passing back complete output items in later turns of the same run. Codex requests go to `https://chatgpt.com/backend-api/codex/responses`, with the workspace header and Bearer obtained from the same token; workspace changes are not accepted after refresh, and unsupported custom parameters are explicitly rejected before the request. See [Codex account authentication](https://developers.openai.com/codex/auth/) and [xAI identity authentication](https://docs.x.ai/build/enterprise) for authorization details.

Grok subscriptions are fixed to `https://cli-chat-proxy.grok.com/v1/responses`; the catalog, Runtime, and settings draft read `ProviderConnectionProfile` together, and an old protocol saved in existing subscription configuration does not change the actual route. Catalog and inference requests both carry a compatible version managed by `ProviderRequestHeaders`, the inference request's `x-grok-model-override` stays consistent with the body model, and the client identity keeps `User-Agent: Eta`. xAI API-key connections still use the user-configured URL and protocol without subscription routing headers. The shared tool catalog and execution contract stay unchanged. Only Grok subscriptions expand union branches whose root has only `required` in the send copy, making them carry outer-object fields and constraints while preserving `oneOf` / `anyOf`; schemas with complete branches or containing references are not speculatively rewritten. Other Providers do not apply this projection, and tool declarations and cache prefixes keep their original generation. See [xAI function calling](https://docs.x.ai/developers/tools/function-calling#parameter-schema) for parameter rules.

OpenAI's initial presets only contain GPT-6.1 Sol, GPT-6 Luna, and GPT-6 Astra, for connections not yet synced. Codex pulls the account catalog from `/backend-api/codex/models`, with the `client_version` query parameter using Atom's release version; it parses the remote `slug`, `display_name`, visibility, input modality, context window, and reasoning tier, without using public-API presets to fill in or filter account models. Grok pulls its catalog from the subscription proxy. After login it auto-syncs the full account catalog, and the model page's manual refresh uses the same path; after a successful sync the remote result is authoritative, while failure keeps the existing configuration. The model list and default selection are driven by persisted configuration; login state does not hide models or switch to another connection, and not-logged-in, expired credentials, and insufficient quota are reported at request time.

Catalog results carry a connection-configuration snapshot and a non-sensitive login generation, verified both at read end and before sync commit, and reading is cancelled when leaving the model page. During sync, matched models keep their local ID and user overrides, auto models are marked as remote-sourced, and auto models removed remotely are cleaned up; manual configuration is kept. Preset updates only clear old presets and add new presets for connections not yet synced, without overriding remote models or refilling when saving an empty connection. The Grok catalog is interpreted by actual inference identifier, hidden fields, and explicitly declared reasoning tiers, without accepting URL or credential overrides from it; protocol filtering and the subscription connection share the same configuration, accepting Responses models declared via `apiBackend` / `api_backend`, with default or null following the connection protocol. When all visible models declare other protocols it reports an error explicitly, not treating protocol incompatibility as an empty catalog.

The provider catalog reads public metadata from the fixed `models.dev/api.json`, with an additional compressed snapshot packed with the APK; the online catalog is atomically cached after size-limit, protocol, and HTTPS-URL checks, falling back to the cache or snapshot on read failure. The catalog only lists candidate models that Atom can connect via Chat Completions and that have text-output and tool-calling capability; reading the catalog does not send saved API keys. After the user selects a model and checks the full Base URL, it is imported as a custom provider that is disabled by default with no API key; the key is later filled in by the user for that URL, and saved models and the current selection are not rewritten by catalog refreshes.

Chat Completions merges all `system` content in the current context into a single first system message in original order at the protocol boundary, compatible with model Chat Templates that require the system message only at the start. Responses projects the complete `system`/`developer` context into `instructions` and rebuilds persisted history into input Items with `type: "message"`.

Chat Completions streaming tool calls are aggregated by `index`, with a later empty ID not overwriting an already-received valid ID. At response end, missing or conflicting IDs are assigned response-level unique values, avoiding IDs already in the original history, actual outbound messages, and this response; the tool-end event and the final call use the same ID. Duplicate IDs in old history are fixed only in the outbound copy: the call batch and the immediately adjacent tool results must be complete and one-to-one pairable, calls and results are renamed in sync, and repeated sends of the same input stay consistent. Ambiguous pairing or cross-message boundaries keep the original record; outbound fixes do not rewrite persisted history, delete results, or re-execute tools.

Responses requests are fixed to `stream:true`, `store:false`, and do not send `previous_response_id`. The Runtime replays the complete output Items returned by the Provider exactly between tool turns of the same run; therefore opaque data such as encrypted reasoning and server-side tool state exists only in memory and does not enter the IPC transcript, Room, logs, or run archive. Persistent sessions keep only normalized answers, visible reasoning content, and Atom tool records, and later runs rebuild context from these stable data.

If a compatible interface omits `output` in `response.completed` or returns an empty array, the Runtime only uses the standard text, reasoning summaries, and function-call increments already received in the same SSE stream to complete the current turn; a non-empty terminal state is always authoritative, and locally recovered results do not impersonate the Provider's opaque output Items.

OpenAI requests encode the thinking tier per the current model's capability configuration, without maintaining a separate request-layer model whitelist; Codex uses the tier provided by the account catalog, and a server-side rejection is returned as-is.

The reasoning UI shows the visible reasoning content returned by the Provider, not generated or supplemented by Atom. Responses supports `reasoning_summary_text.delta` and `reasoning_text.delta`; the terminal state reads the reasoning item's `summary[]` and `content[].reasoning_text`, and is compatible with the legacy interface's single `reasoning_text` field. When standard content and legacy fields coexist it does not append duplicates, and the terminal state still calibrates streaming results by item and content-block identity. Responses only supplements reasoning capability for models that exactly hit the official catalog and are not explicitly marked `reasoning:false` remotely, without assuming all models support reasoning based on the Endpoint type.

Chat Completions consumes `reasoning_content`, and is compatible with visible text or summaries in `reasoning` and `reasoning_details`; when one fragment contains multiple representations it is shown only once. Anthropic consumes existing text in `content_block_start` and subsequent `thinking_delta` / `text_delta`, with thinking signatures and encrypted content not shown as text. All protocols share SSE framing, supporting multi-line `data:`, comment heartbeats, and UTF-8; body, thinking, and tool interpretation remain each Provider's responsibility. Chat ends the visible block when `finish_reason` arrives, then receives usage and `[DONE]`; Responses and Anthropic wind down immediately after their respective terminal events, without waiting for the connection to close. A missing valid terminal state or an unclosed Anthropic visible/tool block returns an incomplete error.

Anthropic tool turns pass back thinking blocks, signatures, and encrypted blocks in original order in the current run's model context for tool results to continue using; these Provider-specific blocks do not enter persistent sessions. When signatures are pending return, the previous turn's system prompt and tool catalog are reused with the original context kept, automatic compression is deferred until the signature turn completes, and forced compression reports an error explicitly; tool execution still follows real-time permission checks. Context compression after the tool turn completes clears old signatures.

Chat Completions, Responses, Anthropic Messages, and Gemini Interactions are uniformly projected at the Provider boundary into body, thinking, and tool blocks with `round + block index` identities. Responses additionally uses `item_id/output_index/content_index` to distinguish multiple output items in the same turn; Chat Completions creates a new block on delta-type switch; Anthropic keeps `content_block.index` directly, and Gemini uses the step index. Body, thinking, or tools do not backfill across block identities; terminal-state calibration or reference completion only updates the corresponding body block, without overwriting the last block with a whole-turn aggregate body.

Server-side web search is an independent switch, off by default. When OpenAI-compatible Responses turns it on, the request adds the `web_search` managed tool; search start and end are projected to the UI as independent run events without entering Atom's local tool executor. When managed search is actually enabled, the model catalog no longer exposes the local `web_search` function; `fetch_url` and `browser_use` are still provided per the local `browserTools` switch. Managed search is not controlled by the local `browserTools` switch. Anthropic and Chat Completions do not enable this switch and do not receive Responses tool fields. `url_citation` in the final answer is deduplicated and converted into clickable Markdown citations; with invalid offsets it degrades to a source list at the end of the answer. File search, code interpreter, Provider-managed MCP, and other managed tools are not currently connected.

Gemini offers two platforms—Google AI Studio (default) and Google Cloud Vertex AI—both using `x-goog-api-key`. AI Studio uses the native Interactions API, fixed to `stream:true`, `store:false`, with Atom providing the complete input. Each `step.start/delta/stop` accumulates by index, and only after `interaction.completed` explicitly enters `requires_action` are complete function calls handed to the local executor.

Vertex AI conversations use `streamGenerateContent?alt=sse` on the standard project endpoint, supporting the Gemini 4 series. The official URL uses the Project ID or project number, with `global`, `us`, `eu`, and single regions using the corresponding official hosts. A custom HTTPS proxy keeps the configured domain. Chat and the `:countTokens` connection test both request the configured route directly and reject HTTP redirects. The connection test uses the currently enabled selected model or a preset for the new connection's region. The Google Search managed-tool switch is only for AI Studio; Vertex AI conversations use Atom's local web search, sharing the tool catalog with local functions.

Vertex AI only commits an answer or executes a complete tool batch after receiving a complete `STOP` terminal state. `MAX_TOKENS` and `CONTINUATION` report the reply as incomplete, and already-streamed body text is still visible in the run UI. Tool results keep the original function ID, and screenshots are placed into `functionResponse.parts` per function call, used only by the model request receiving that batch. Atom keeps an independent local identifier per call, and screenshot data does not enter persistent sessions. Vertex AI's explicit thinking tier is validated against Gemini 4 model capabilities.

Cumulative usage for both platforms overwrites prior values per field and is published uniformly at the terminal state. Context usage shows the server's `total_tokens` or `totalTokenCount`, automatic compression uses input tokens, and cached tokens are already included in the input. Custom request headers and bodies cannot override auth, input, the tool catalog, streaming fields, or session-saving policy. HTTP 400 can show a controlled error type and parameter-field position.

Gemini tool parameters do combination-branch compatibility projection at the Provider boundary: when `required` inside `oneOf`, `anyOf`, or `allOf` branches references an already-declared outer property, the missing local definition is supplemented for that branch, preserving the original required, combination, and additional-properties constraints. The conversion does not modify the public tool catalog, does not propagate properties across nested objects or arrays; references and resource identifiers keep their original positions, and branches restricting additional properties do not inherit declarations from the outer level, avoiding changing schema semantics.

Gemini's complete native steps, thinking, and search signatures are replayed only within the current run and do not enter the stable session or run archive. While the signature tool chain is incomplete, the request prefix is kept and automatic compression is deferred, with forced compression failing explicitly. Across runs, Providers, or after compression, old messages and tool records are projected as clearly-marked text history, without reconstructing old tool exchanges that lack signatures into native calls. AI Studio's tool screenshots follow the single-turn observation message after a complete tool batch. Thinking configuration resolves in the order of user override, remote metadata, and locally known defaults. AI Studio's unknown models default to only Default; the model edit page allows manually checking Minimal, Low, Medium, High, and XHigh of the Interactions protocol, with the server validating whether the specific model supports it, and request failure reporting explicitly without automatic degradation. Turning off "Configure thinking tier" only restores Default without sending a parameter to turn off model thinking; restoring auto removes the user override. Tool-mixing capability is still confirmed independently and not inferred from the manual thinking configuration. The native model catalog supports pagination and caps cumulative size, and existing compatible connections are not auto-converted to Gemini. Gemini 4 Neon (`gemini-4-neon`) and Gemini 4 Hydrogen (`gemini-4-hydrogen`) support Default, Low, Medium, High, and XHigh, with the server defaulting to High and thinking not disableable; Gemini 4 Carbon (`gemini-4-carbon`) supports Default, Low, Medium, and High, with the server defaulting to Medium and thinking not disableable; these models are all added to built-in presets, old installs only get the new items, and existing same-ID models are not replaced. Requests specify the tier via `generation_config.thinking_level` and request summaries with `thinking_summaries: "auto"`; `thought.summary` and streaming `thought_summary` are used for display, signatures are not shown as text, and the server may return only a signature without a summary. See [Google thinking documentation](https://ai.google.dev/gemini-api/docs/thinking) for the parameter contract.

Gemini Google Search takes effect only when the user enables it, the model is confirmed to support it, the entry declares it, and the Runtime validates that suggestions can be shown. Atom chat and the native assistant overlay support this capability; older clients and other entries keep local search. Mixing search and functions uses `validated`, and the capability is currently a preview. The complete signature replay of search calls and results stays at the model layer, and citations are converted by UTF-8 byte position; search suggestions attach below the corresponding answer, with tool turns without body text deferring suggestions to the next answer. Suggestions are shown in an independent read-only WebView with scripts, file access, and network subresources off; tapping an HTTP(S) link hands it to the external browser.

Search suggestions use `SearchSuggestionsPayload`'s single-fragment, per-turn count, and total-byte budgets, failing explicitly when exceeded without truncating HTML. An active Runtime's in-memory reconnect can replay suggestions; persisted events, checkpoints, archives, session storage, backups, and exports all exclude suggestion HTML. Process recovery keeps only answers and citations, and cannot restore the original suggestions. `store=false` only controls Interactions saving and does not promise to disable Google Search's own data processing and retention; see the [official notice](https://ai.google.dev/gemini-api/terms#grounding-with-google-search).

### Model Waiting and Retry

The model stream uses an independent HTTP configuration: 15-second connect wait, 30-second write wait, 5-minute read wait; the read limit targets waiting for new data, not the whole task's total time limit. MCP, model lists, and downloads keep their own configurations. The model HTTP client turns off underlying connection auto-retry, and the model turn's bounded retries are orchestrated uniformly by the Loop.

Connection interruption, timeout, early EOF, temporary rate-limiting, and some server errors retry at most 3 times, waiting 2, 4, and 8 seconds in sequence; each successful model turn regains an independent budget. Auth, quota, billing, certificate, and protocol-format failures, and other non-transient failures, are not auto-retried. Retry waits are cancellable and obey pause checkpoints; queued steering is left until the current turn and tool batch complete.

A failed attempt does not commit assistant history or execute its local tool calls; previously completed tool results, the current turn's tool schema, and screenshots stay unchanged during retry. A retry uses a new display turn, the failed half-output stays in the run trace marked as retried, and subsequent output is not concatenated onto old blocks; the final reasoning summary does not include the replaced failed attempt. Retry events are saved through the existing IPC, checkpoint, and archive encoding, and recovery replay does not re-execute tools. If the Provider already reported a managed tool as started, this failure is not auto-retried, to avoid re-triggering a server-side operation.

## MCP Tools

Atom directly acts as an MCP client connecting to remote Streamable HTTP servers, without binding the protocol capability to a specific model Provider. It currently prioritizes the `2026-07-28` stateless protocol and is compatible with `2025-11-25` services that require `initialize` and session; it only connects `tools/list` and `tools/call`, and does not yet support Resources, Prompts, Tasks, stdio, OAuth, interactive supplementary input, or Provider-managed MCP.

Tools are off by default, and a server can also be disabled wholesale. When adding a server, it first discovers and caches the tool catalog, then the user enables items one by one; tools not marked read-only require extra confirmation. Modern services' catalogs expire by `ttlMs` and refresh before the next run, while legacy catalogs are manually refreshed by the user. Tool discovery follows the MCP cursor-pagination spec (treating `nextCursor` as an opaque string and ending only when the field is missing or `null`), supports at most 2048 tools, 64 pages, and a 2-million-character catalog budget per server, and persists oversized tool catalogs through a chunked table; if it still hits a protection bound or detects a duplicate cursor, it records the truncation reason and shows it clearly in the UI, without silently dropping. At each run start it freezes the enabled catalog and Bearer Token together and generates a server-namespaced model tool name, so later setting changes do not alter the executing schema or account. Atom does not disable tools because of complex schemas like `$ref`, combination keywords, or conditional keywords; instead it keeps the parameter declarations, lets the Provider adapt its interface format, and hands the actual parameters to the MCP service to interpret; modern Streamable HTTP's `x-mcp-header` parameters are mapped to request headers in sync.

MCP URLs are configured directly by the user, with HTTP, HTTPS, LAN, and local addresses using the same connection chain and the shared OkHttp client's default redirect and timeout behavior; HTTP transmits tokens, tool parameters, and results in plaintext. The Bearer Token is encrypted with the Android Keystore and stored locally. MCP raw parameters and results are used only in the current turn, and the persistent transcript, run checkpoint, and archive keep only redacted records; text, structured results, images, pagination count, and per-run tool count still have independent budgets, and unsupported or over-budget results carry explicit markers. Cancelling a run immediately closes new calls and in-flight HTTP requests, and legacy session release is only async best-effort, without blocking the cancel thread.

## Long-Term Memory

The default assistant's real-world long-term memory is kept in `MEMORY.md` in the app private directory. The file uses UTF-8 with a 1 MiB safety cap; the repository applies changes under an in-process lock and overwrites the complete file via `AtomicFile`. Model writes carry the current content's SHA-256 revision; when the revision does not match it returns `MEMORY_CONFLICT` without overwriting concurrent updates. Character story uses an independent file and reuses the capacity, atomic-write, and conflict-check rules.

Each run only puts the in-budget content of `# Core memory`, the first/second-level heading index, and the revision into the system background. The core budget is `min(32000, max(4000, contextWindow / 16))` characters; when the model window is unknown it is computed as 128K. Without a `# Core memory` heading, no body is auto-injected. The rest is retrieved by `memory_get` by line pagination or text search, returning at most 32000 characters per call.

`memory_write` supports line-range replacement, independent-section append, and clearing; a single model-generated content is at most 3500 characters, while the settings page's manual user editing is not subject to this single-tool limit. Turning memory off does not delete the file, and later runs no longer inject or expose the tool; an already-started run also re-checks the switch before each memory-tool execution.

Memory content only serves as editable background and has no instruction priority. Memory-tool raw parameters and results are available to the current Agent Loop, but the corresponding tool calls are fully redacted in the persistent transcript; run events save only the operation type, line count, byte count, and error code, not body text or query terms.

## Local Tool Capability Contract

`AgentToolRequirements` declares for each local tool the `NONE / PARTIAL / REQUIRED` Root requirement plus accessibility, ordinary system authorization, and ROM conditions; a tool without registered metadata cannot enter the model catalog. `AgentToolCapabilities` captures device conditions each turn, and the projected schema is used for Provider declarations, from which the Loop determines the tool names callable this turn. Metadata is internal to Atom and does not extend the Provider protocol. UI aggregate cards associate real tool IDs, and "All capabilities" only changes presentation.

Without Root, dedicated tools are removed entirely; the terminal family and file tools only expose the available `identity=user`. The default identity and workspace already selected for this run stay unchanged, and the model context describes the current permission and default environment at the same time. The executor checks current Root by actual execution identity, with invalid privileged calls returning `ROOT_REQUIRED`. Ordinary foreground Intents do not require accessibility; screenshots, nodes, gestures, input, and conditional waiting require a real service connection, keeping a limited repair chain when system protection is enabled. Current notifications come from the connected notification-listener service, returning an explicit error on disconnect without substituting history records. User choices are saved in the existing local Agent configuration and RemotePreferences coordination chain, and capability changes do not rewrite saved switches.

Root probing runs on an IO thread: when `su` exists, it auto-requests once on first use, waits at most 30 seconds, and only UID 0 counts as available; denial and timeout do not repeatedly pop requests on ordinary refreshes. The model context distinguishes probing, unknown, no `su` found, unconfirmed, denied, timed out, and authorized, and must not interpret the default `identity=user` as no Root support. When the user states authorization or needs re-confirmation, it can call `terminal(action=check_root)` to run the fixed `su -c 'id -u'` and update the authorization state, or retry manually under "System enhancements". The check action may show a system authorization request. The capability catalog and prompt use the same state snapshot, updating the prompt when the check state changes, without waiting for the authorization boolean to change. The LSPosed connection is judged independently and does not substitute for Root authorization.

## Web Search and Body Reading

Local `web_search`, `fetch_url`, and `browser_use` share the existing `browserTools` permission; when Responses managed search is enabled, the local same-name search is no longer exposed to the model, while body reading and the browser stay available. The setting text is "Enable web search, reading, and browser", and the persisted key is still `agent_browser_tools`; when off, the catalog does not expose these three local tools and the execution entry re-checks the switch each time. They require no Root or accessibility service; model requests, MCP, and Provider managed search still follow their own configuration and authorization chains.

`web_search` and `fetch_url` keep a unified model-tool contract, and the underlying execution backend can be separately selected in the "Web search and reading" settings as **Built-in default**, **DeepSeek** (`POST /v1/tools/search` and `POST /v1/tools/fetch`), or **Custom interface** (supporting GET/POST, request templates, and response JSON path mapping). Non-sensitive settings are saved in `SettingsDataStore`, and the independent API key is encrypted with AndroidKeyStore `AES/GCM/NoPadding` and saved in `eta_web_tools_secrets`; when DeepSeek is selected and no separate key is filled in, the DeepSeek API key and service URL already configured in the model provider are reused automatically.

`web_search` by default requests DuckDuckGo's public HTML search entry (`scope=first_page`) through `PublicWebSearch`, and can switch to DeepSeek Search or a custom search interface (`scope=api`). `max_results` defaults to 5 and is at most 10; it returns target-site titles, original links, and summaries (the DeepSeek backend additionally attaches a long `summary`, site name, publish time, authority, and ranking score), strips redirect wrappers, and deduplicates. Results carry collection time, truncation reason, and skip count; verification challenges, auth or balance failures, HTTP rate-limiting, encoding failures, oversized responses, or unrecognized response structures return explicit errors.

`fetch_url` supports the built-in local anonymous HTTP GET, DeepSeek Fetch (returning Markdown), or a custom read interface; when configured as DeepSeek or a custom interface and the remote fetch fails (not cancellation, not URL-format error), it automatically falls back to local static fetching and marks `fallback_from` in the result. Local HTML parsing only processes downloaded text, without executing JavaScript or loading page subresources; besides HTML/XHTML it also accepts `text/*`, Markdown, JSON, and `application/*+json`. Character encoding is judged by BOM, response headers, and any available HTML declaration; replacement decoding of the body marks `decoding_lossy`. It does not inherit the shared WebView's cookies or login state; use `browser_use` when dynamic rendering, login, forms, or other web interactions are needed.

The first read passes `url`, and continuation pages pass the returned `document_id` and `next_offset_chars`; exactly one of the two sources must be chosen. Pagination reads the same cached body without repeating the HTTP request and without mixing in content the site updates later. The snapshot belongs only to the current run, keeps at most 4 documents with a combined body of at most 600000 characters, evicts by recent access; run close clears it, and invalid or cross-run IDs return `WEB_DOCUMENT_EXPIRED`. Character offsets must use tool-returned values and must not land in the middle of a Unicode surrogate pair. `has_more` means the cached body still has a next page, and `source_truncated` means the download or extraction itself lost content; reading all pages cannot eliminate source truncation.

Network and body budgets apply separately:

| Boundary | Current limit and result |
| --- | --- |
| HTTP request chain | At most 30 seconds total, at most 5 redirects followed; loops, timeouts, and invalid jumps fail explicitly without auto-retry. |
| Response body | At most 2 MiB read; search responses over the limit fail, web body reads keep the truncation marker. |
| Text parsing | At most 512000 characters of input processed; search over the limit fails, web extraction marks `input_limit`. |
| Single-document body | At most 200000 characters kept, marking `content_limit` when exceeded. |
| Single-page body | Default 12000, at most 16000 characters; links and titles have separate count, text budget, and truncation markers. |

`WebHttpTransport` only accepts HTTP(S), rejects URLs with a username or password, and strips the fragment. Every hop checks protocol, URL credentials, and the redirect budget; it allows accessing addresses reachable on the current network and does not additionally intercept DNS, IP, LAN, or local addresses, so it cannot be described as a network security sandbox. Requests are still subject to system network authorization and connection conditions. Cancelling or closing the run cancels currently owned HTTP requests, and body extraction and cache reads also check the cancel state. The authoritative source for parameters, status codes, and budgets is [AgentWebToolCatalog](../app/src/main/kotlin/io/github/namanwtf/atom/agent/model/AgentWebToolCatalog.kt), [WebHttpTransport](../app/src/main/kotlin/io/github/namanwtf/atom/agent/web/WebHttpTransport.kt), and [WebPageContent](../app/src/main/kotlin/io/github/namanwtf/atom/agent/web/WebPageContent.kt).

Search summaries, web body text, and links are all marked as untrusted external data and cannot modify tool permissions or override Runtime instructions. Answers cite search results using the title and the returned original target URL; citing a read page uses the title and `final_url`, without treating the internal document ID as a source or passing off a search summary as complete-reading evidence. Run summaries show only actions, hosts, and counts, without echoing query terms, full URLs, body text, or raw server-error text; the raw tool exchange still enters model context and conversation records as an ordinary tool result.

## Structured File Tools

File tools are declared uniformly by `AgentFileToolCatalog`, dispatched through `FileToolDispatcher`, with `AgentFileOperations` handling text and editing contracts and the backend handling paths, metadata, and I/O in the current environment. The model can call the following tools directly without concatenating Shell commands for ordinary file operations:

| Tool | Current contract |
| --- | --- |
| `read_file` | Bounded UTF-8 text reading, positioned by byte or start line, returning the actual content range, `revision`, and `next_offset_bytes`. |
| `write_file` | Create, fully overwrite, or append UTF-8 files, creating parent directories when needed; supports `expected_revision` prechecks. |
| `edit_file` | Exact replacement of `old_text`; by default must match uniquely, replacing multiple places only with explicit `replace_all=true`. |
| `stat_file` | Query canonical path, type, size, and version, without reading body. |
| `list_directory` | Return structured pagination of direct children, continuing enumeration with `next_offset` and the directory version. |
| `glob_files` | Recursively find files by `*`, `?`, `**` path patterns, with cursor continuation. |
| `grep_files` | Search single-line literal text in UTF-8 text, returning file path, line number, and bounded fragment; case-sensitive by default, no regex, no dependency on a device `rg`. |

File operations are bounded overall by a 20-second time budget and Runtime cancellation. All file tools share `environment`, `identity`, and `cwd`. `environment=android` shares this run's default identity and workspace with the terminal, defaulting to Root when Root authorization is confirmed and otherwise to the app identity; both default to the app workspace, `identity` no longer implicitly switches directories, and `cwd` only overrides the current call. The workspace page reads and exports through the corresponding file backend, supporting Root-generated files. Ordinary-identity file-system access sets no extra directory whitelist, and the access result after resolving absolute paths, relative paths, and symlinks is decided by OS permissions. `environment=linux` uses the user-selected distribution and PRoot/chroot backend, with paths and symlinks interpreted inside that Linux environment and the default working directory `/workspace`; host rootfs paths cannot substitute for in-Linux paths, and there is no automatic environment switch or identity upgrade after a failure. UID 0 shown inside PRoot does not mean having Android root permissions.

`read_file` shows at most 16000 bytes of visible text per call, and the cursor only crosses fully-decoded UTF-8 characters. Continuation uses the returned `next_offset_bytes` with `expected_revision`, and cannot derive the next segment from the requested `max_bytes`. Non-UTF-8, binary content, or byte offsets landing mid-character return explicit errors. `max_lines` and the byte budget apply simultaneously, an over-long single line may be segmented and marked `line_truncated`; `start_line` positioning also has a scan budget, and `start_line_reached=false` must not be treated as having read to the target line or end of file. A version change detected during reading returns `FILE_CHANGED`.

Single-write content, the precisely-edited original file, and the post-replacement file are all bounded by a 512 KiB cap. `edit_file` fails explicitly on no match, multiple ambiguity, or version change, without writing a guessed result; it also checks the read complete-old-content digest before committing. `revision` is an opaque metadata version generated by the backend, usable only within the same environment and identity, not a cross-process file lock, and cannot replace content checks during editing.

Write returns `atomic`, whose meaning depends on the backend:

- The Android ordinary-identity Java file backend stages in the same directory, syncs content, then atomically moves to overwrite; when atomic move is unsupported it returns `ATOMIC_WRITE_UNSUPPORTED` rather than falling back to ordinary overwrite. Append writes return `atomic=false`. Before overwriting, it tries to preserve the original POSIX mode only when permissions actually differ; a necessary permission-copy failure keeps the original file and reports an error explicitly. `atomic=true` only describes the visibility of the target-path replacement, and does not promise mutual exclusion with external writers or preservation of the original inode, hard-link relationships, or all file attributes.
- The Android Root and Linux Shell file backends write through the existing inode, preserving the existing file's owner, mode, and SELinux label, and return `atomic=false`; interruption may leave a partial write. Version and content checks do not turn this write into an atomic transaction.

A Shell subprocess may close the input pipe early on validation failure or cancellation, and the executor keeps its failure exit code, converted by the file backend into a corresponding error like `FILE_CHANGED`. When the subprocess returns success but input transfer failed, the file tool returns `FILE_INPUT_FAILED` and does not report an incomplete write as success; re-read and confirm the file state at that point.

Directory continuation uses `next_offset` and `expected_revision`; the offset points to the original directory enumeration position, and hidden-item filtering may make one page return fewer items, which must not be taken as the end. `has_more=false` means enumeration is complete. Directory changes invalidate the cursor. The whole-directory paginated JSON is at most 16000 characters, stopping before a not-yet-returned item when the output budget is reached and keeping the continuation position; `stop_reason` distinguishes `eof`, `entry_limit`, and `output_limit`. Underlying directory enumeration, a single path, or metadata over the limit returns an explicit failure.

Recursive search skips hidden directories by default and does not follow symlinks; entry count, read bytes, result count, output text, and recursion depth each have budgets. Search also has a roughly 5-second soft time budget, returning obtained results and a continuation cursor as `time_limit` when a checkpoint hits the budget; a single blocking operation is still terminated by the whole 20-second cap, and a hard timeout, cancellation, or execution-process failure is not disguised as an ordinary skipped file. Continuation passes back `next_cursor` verbatim and keeps query conditions, environment, and identity unchanged. `partial`, `complete`, `stop_reason`, and skipped items together describe coverage; when the current scan or result budget is reached with a valid cursor you can continue, skipping binaries, inaccessible items, or over-deep directories keeps an incomplete marker, and an empty match does not mean no file contains that content. Complete parameters and limits are authoritative from [AgentFileToolCatalog](../app/src/main/kotlin/io/github/namanwtf/atom/agent/model/AgentFileToolCatalog.kt) and the corresponding backend implementations.

These tools only accept file-system paths and do not directly accept or write back document URIs such as `content://`. A selector import returns a workspace copy, and editing the copy does not mean modifying the source document; the app file page's import/export and the model file tools are different entries. There is currently no dedicated file-copy, move, or document-export tool.

## Structured Device Query and Operation

`get_current_context` shows as "Read time and location" in operation records, and the result keeps the local time and UTC offset returned by the phone. Location shows the system's most recent location record and its age; with no authorization, system location off, or no cached location it prompts explicitly, without describing a cached location as a live fix or additionally resolving a city or address.

`inspect_app` is a device direct-access tool, preferring PackageManager to query an exact package name without requiring the target app to have a launcher entry. The result includes version, UID, install source and path, enabled/stopped state, and a paginated permission list. The query targets only the Android user Atom belongs to; when `user_id` is missing that user is used, and specifying other users or work profiles returns `USER_SCOPE_UNSUPPORTED`. With missing package visibility, a failed query is not directly asserted as uninstalled, and an unreadable install source is also marked separately.

`get_logcat` is still a sensitive-read tool requiring Root. It first collects the most recent `scan_lines` records by PID, tag, minimum level, and buffer, then filters within the sample by the ISO 8601 `since` and literal `query`, returning at most `max_lines` entries plus limited text. Logs are device-scoped and cannot use `user_id` to fake user isolation. The result's capture start/end, `scan_limited`, `capture_truncated`, `has_more`, and `complete_within_scan` describe the capture and return ranges respectively; `has_more` only means there are unmatched items in the sample. The log source is a ring buffer, so `history_complete` is always false, and no match does not mean earlier records do not exist.

`get_setting` and system write operations uniformly specify or report `user_id`, no longer treating the foreground user in Root commands as the user Atom belongs to; no cross-profile backend is currently provided. `global` settings and Wi-Fi/Bluetooth are device-level states. `set_setting`, `set_device_state`, `app_state_control`, and `set_volume` return `before`, `after`, `expected`, `changed`, and `verified`; command exit 0 or API acceptance no longer equates to the target state taking effect. Reading back a value that has not reached the target or whose transition state has not ended returns `STATE_CHANGE_UNCONFIRMED`; when before/after cannot be compared, `changed` is null. An already-at-target state can verify successfully with `changed=false`. Verified device operations show the specific target and before/after states in records, e.g. "Auto-rotate: off → on"; volume, brightness, and screen-off time use the read-back value with its unit, and an unknown prior value is not inferred as zero or off. General settings show values only for semantically clear fixed setting keys, keeping a modification summary without raw values for the rest.

## Personal Context and First-Party App Operations

The tools page groups "Personal context" and "System and app operations": the former finds and understands user information, and the latter modifies calendars, alarms, notes, and system state. The grouping describes product responsibilities, while permissions still follow the independent device-direct, sensitive-read, and sensitive-action switches. The model calls domain tools directly, and basic app operations do not depend on Skills.

### Personal Context

The model catalog uses explicit entries such as `search_notes`, `search_system_memories`, `search_bills`, and `search_flights`, without exposing a `personal_context(action, source)` universal tool. The old `search_coloros_notes` and `search_coloros_memories` names are compatible only at the execution layer and do not reappear in the model catalog. Contracts are at [AgentPersonalSearchToolCatalog](../app/src/main/kotlin/io/github/namanwtf/atom/agent/model/AgentPersonalSearchToolCatalog.kt) and [AgentDeviceToolCatalog](../app/src/main/kotlin/io/github/namanwtf/atom/agent/model/AgentDeviceToolCatalog.kt) respectively.

- Raw sources such as media, files, contacts, SMS, calls, recordings, and notes use typed Provider queries; schedule reads use the Calendar Provider. Fixed URIs, fields, and parameters are managed by the executor, without exposing SQL or arbitrary Providers to the model.
- `search_media` and `search_files` search names against raw sources by default, and `match=content` queries the ColorOS content index. `search_notes` prefers reading raw notes; when the source is unavailable it can return a clearly-marked historical index, and `current_only=true` forbids this fallback. Empty-cursor interfaces and zero-record results are handled separately.
- Bills, to-do clues, calendar to-dos, memory collections, life events, and itinerary tools use the ColorOS DMP index, requiring Root and a compatible system source. Source availability, field coverage, and result freshness are authoritative from this result. The index may be delayed, incomplete, or retain old records, and cannot prove "just created" or "currently exists"; inferred events are not verified facts.
- Index queries return a `ref`, read in detail by `read_personal_item`. That reference cannot be used as a calendar event_id, an alarm alarm_id, or a note UUID; the original object identity must be found and verified before operating.

Index-query keywords are at most 200 characters, a page defaults to 10 and is at most 30 items, and the offset range is 0 to 10000. Time uses ISO 8601 with offset, over `[start_time, end_time)`. Memory collections have no confirmed business time field and do not support time filtering. Pagination faces a changing index and does not promise cross-page snapshots; results report continuation, truncation, field-missing, and time semantics separately. A recording-transcription path is not the transcription text, and historical notifications do not represent the current notification shade.

`summarize_bills` fully processes at most 1000 matched records, summing with `BigDecimal` in yuan/CNY; over the cap, invalid amounts, or truncated input it fails without returning a partial total. Income, expense, transfer, and unknown types are listed separately; negative amounts accumulate as-is without inferring a refund net. It shows at most 20 categories, merging the rest into `other_categories`. Results cover only the matched system index and do not promise bank-ledger completeness.

Raw personal-data parameters and results are only for the current model turn and do not enter the persistent transcript; the model's final organized answer is still saved as an ordinary conversation.

### First-Party App Operations

[AgentPhoneToolCatalog](../app/src/main/kotlin/io/github/namanwtf/atom/agent/model/AgentPhoneToolCatalog.kt) centrally declares the new entries and their permission metadata. `agent/phone/` divides executors by calendar, clock, note, and system operations; the Root channel transmits typed requests over standard input, calling Atom's fixed entry via `app_process`, with parameters not concatenated into Shell commands. Root identity uses the real calling attribution without impersonating the system-assistant package name.

| Domain | Capability and boundary |
| --- | --- |
| Calendar | List writable calendars, read events, create single or batch events, modify and delete. Can use ordinary calendar read/write permission or Root; multiple calendars require an explicit choice. Events and reminders are written in a transaction, with batch up to 30 items. Recurring events are not currently edited, and deleting a whole series requires explicit `scope=series`. All-day time uses UTC midnight and an exclusive end date. |
| Alarm | Keeps standard Intent creation and timer entries; the ColorOS-compatible Root channel supports create, read, modify time, enable/stop, and precise delete. Modifying time keeps the original enabled state; an explicit vibrate parameter uses the standard Intent to avoid vendor interfaces ignoring it. |
| Notes | The ColorOS-compatible Root interface supports create, read by UUID, and move to trash; rich-text editing is not yet provided. It checks the read interface is ready before creating, parses the business return value, and reads back to verify, without claiming success from a non-empty URI. |
| System | Flashlight toggle and state; brightness, auto-brightness, rotation, screen-off time, dark mode, and eye-comfort mode; volume, ringer, and DND; Wi-Fi, Bluetooth, mobile data, airplane mode, location, NFC, battery saver, and personal hotspot. Specific Root, permission, and ROM conditions are reported by tool metadata and execution results. |

The flashlight uses CameraManager callbacks to verify state; system switches read the actual state, and app operations read the raw record. Request-accepted, command-exit-success, and state-confirmed are handled separately. Timeout after write, incomplete response, or read-back failure returns `unconfirmed`, and state should be queried first, without auto-retrying creation. When the system interface is unavailable it returns a specific failure, without writing unconfirmed database fields to fake business-operation completion.

## Terminal Environment

Terminal tools are divided into three entries by lifecycle, reusing the same permission switch and execution context:

| Tool | Invocation | Lifecycle |
| --- | --- | --- |
| `terminal` | An ordinary call only needs `command`, with `action` defaulting to `exec`; `open` creates a session, `session_id` reuses it, `close` closes it. | Commands and sessions belong to the current Agent run, with the process reclaimed after a single call ends; not used to hang background processes with `&`. |
| `terminal_job` | `start` launches, `list` views tasks, `read` reads logs, `wait` waits for completion, `stop` stops. | Continues after the reply ends; notifies the user on completion, failure, or stop, with status and logs queryable in later runs. |
| `terminal_daemon` | `start / list / logs / stop` manage background services, using `task_id`. | Can run across runs, and may still end due to process exit, system reclamation, or reboot. |

Parameters are declared by `AgentTerminalToolCatalog`, and the executor reads required fields per action, without a separate field whitelist or schema precheck. With `session_id`, the session's directory, identity, and environment are reused, and repeated `cwd`, `identity`, `environment` do not override the session. Async tasks and background services do not reuse the Shell session. Commands have no app-side character cap, and actual running is still subject to system process limits, timeout, output budget, and cancellation. The legacy `run_command` and old terminal actions keep only historical display and are no longer execution entries.

`TerminalExecutionContext` freezes the working directory, selected Linux distribution, and rootfs path at run creation, and the same object provides facts to the executor and model. New Android calls choose the default identity by current confirmed authorization: Root directly when available, otherwise the app UID; an explicit `identity` takes priority. Existing sessions and background tasks keep their creation identity, and authorization changes do not move files. The model's first turn waits for the Root probe already started by the app, not letting a probing Root user first try as ordinary identity; with an existing valid authorization there is no need to re-call the check tool. The background service's launch backend is bound to the same context and does not follow mid-run Linux-setting changes. The model can see the actual working directory, Linux backend, base-rootfs and common-tool/extension readiness, and the `/workspace` host mapping, avoiding treating the PRoot private workspace and the chroot Root workspace as the same directory. Persistent directories, task records, and existing Linux installs are not migrated.

The terminal family's and file tools' `environment` clearly distinguishes device control from general Linux tools, defaulting to `android`:

- `android` continues using the system Shell. Files and commands default to `root` when Root authorization is confirmed and `user` otherwise; the same private workspace does not switch with identity. `user` is Atom's app UID, not equivalent to ADB Shell, and does not upgrade permissions because a command failed. The `root` identity probes Magisk, KernelSU, APatch, or system BusyBox inside `su` and prefers standalone `ash`, so BusyBox applets do not need to be pre-added to PATH.
- `linux` resolves the user-selected distribution and backend. chroot keeps the original rootfs, independent mount namespace, `/data/local/tmp/atom` workspace, and privileged mounts. New PRoot environments and ordinary workspaces use the `filesDir/terminal-user` directory exclusively owned by the app UID, avoiding the old Root directory's ownership limits; existing ordinary environments keep their original location, paths are uniformly resolved by `TerminalPrivateStorage`, and `/workspace` maps that private workspace. Only accessible shared directories are mapped, and import/export still works after denying "All files access". A simulated root inside Linux does not mean Android root, and neither backend constitutes an isolated security sandbox.
- Established sessions and tasks save their backend and actual rootfs/workspace, without auto-switching when Root changes. The backend and host-workspace fields of persisted task records are optional, compatible with old records. Gaining Root does not migrate PRoot, and losing Root does not delete chroot or change file ownership.
- Ordinary Android Shell and file backends use the app UID; the Root file backend accesses target paths through authorized su. Image reading follows its own authorized-file-reference rules. Selector files that cannot be accessed directly are imported into the workspace via bounded copy; directory selection cannot impersonate a live-accessible path.

The terminal samples `runtime` metadata in the actual command Shell, including `host_identity`, `uid`, `uid_scope`, `shell_provider`, `shell_executable`, and the resolution results of a set of commands. Linux's UID belongs to the guest environment and cannot infer host permissions from it; resolving `cmd`, `pm`, or `dumpsys` does not mean the current identity is authorized to access the corresponding system service. Incomplete sampling reports missing, without guessing Bash, GNU tools, or `rg` from the device version. Android native processes are still subject to the [App UID sandbox](https://source.android.com/docs/security/app-sandbox), and Root processes are also affected by [SELinux](https://source.android.com/docs/security/features/selinux) policy.

Synchronous command timeout terminates execution, and an in-session timeout also closes the session. Background commands are outside the Agent run's process-reclamation scope; cancelling the conversation or waiting does not stop an already-submitted command; use `terminal_job(action=stop)` or the terminal page to stop it. Background commands have a default runtime cap of ten minutes, and `timeout_ms=0` disables the timeout. `wait_ms` only limits the wait duration, returning current status on timeout without terminating the command.

Background output is written directly to the log; `read` returns a bounded tail preview and `output_path`, and the full log can be paged-read with the original identity through the Android file tools. Task results distinguish `completed / failed / timed_out / stopped / interrupted`, with a real `exit_code` kept on exit failure; success is not reported when the exit code cannot be confirmed. Logs are kept after the task ends, and old tasks with handled completion notifications are cleaned by the existing task-record retention count.

Background commands reuse `DetachedTaskSupervisor`'s persisted records and `ShellProcessSupervisor`'s process ownership and process-group reclamation. `terminal-daemons.json`'s producer is still that host, and consumers are model tools, the background observer, and the terminal page; the new command type, description, timeout, completion time, exit code, end reason, and notification state are all optional, with old records read as background services. New commands additionally write a `.exit` status file, and app rebuild only claims or reads existing results without re-executing commands. The background observer is held by `AgentExecutionService`, and completion notifications contain only the task description and result, without raw commands or logs; tapping the notification goes to the terminal page to view the task. Notification display depends on system notification permission, and the tool result's `completion_notifications_enabled` reports current availability; the terminal page and task query always keep the result.

The user chooses one current Linux distribution between Alpine and Debian, and the model and terminal uniformly use that choice via `environment=linux`. Base-environment install and base-tool install are two independent steps: the installer first downloads a rootfs with fixed version, size, and SHA-256, extracts it in a temporary directory, and writes the base-completion marker only after a successful runtime check; PRoot's streaming unpack verifies archive paths and links and supports cancellation and failure cleanup; the user then installs a base tool set containing only common commands. The Python profile only installs uv, which then installs the latest stable Python to `/opt/eta/python` and links global commands to `/usr/local/bin`. The Node.js profile installs the upstream latest stable ARM64/x64 artifact on Debian and `nodejs-current` from the stable branch on Alpine; SSH uses the selected distribution's latest stable package. The app side only reads the installer completion marker, no longer re-checking symlinks, binaries, or execute permissions inside the rootfs. Under mainland-China networks, Alpine uses the Alibaba Cloud mirror, the Debian main repository uses Tsinghua TUNA and security updates use the Debian official source, each keeping only the official main repository as a failure exit; APT also enables retries and disables HTTP pipelining.

APK analysis shows as an optional profile in both Alpine and Debian. JADX, Apktool, smali, and baksmali use the current latest stable's fixed official Release URL, size, and SHA-256, entering the app-writable cache staging only after full verification; the download or unpack staging directory cannot be placed inside a Root-created Linux management directory. GitHub artifacts first try one HTTPS download entry before returning to the official URL, but still only accept bytes fully matching the official manifest SHA-256. JADX only extracts the CLI scripts, runtime library, and license, atomically switching the current version after all commands verify. The profile installs `openjdk25-jdk` on Alpine and `openjdk-25-jdk-headless` on Debian, without installing global Gradle, Android SDK, or NDK. Because Google's Linux SDK, AAPT2, and NDK host tools only provide x86_64 builds, a phone ARM64 chroot cannot natively assemble a complete officially-supported Android build chain; `apktool build` is therefore stably rejected, while decompiling, code viewing, and standalone Smali assemble/disassemble are unaffected.

Debian base-tool install refreshes the `eta-apt` entry, so an interrupted old-environment init can be retried directly. The entry checks package state and dependencies with `dpkg --audit` and `apt-get check` before installing; on anomalies it first tries to complete unconfigured packages, runs `apt-get --fix-broken --no-remove install` when necessary, then reconfigures and verifies. Recovery relies on the package manager's own state, and automatic repair does not remove packages. When repair is incomplete or installation leaves an inconsistent state, it stops the operation and prompts with the check/repair failure and a manual diagnostic command; timeout and other install failures are no longer uniformly blamed on the network. See Debian's [dpkg manual](https://manpages.debian.org/trixie/dpkg/dpkg.1.en.html) and [APT manual](https://manpages.debian.org/trixie/apt/apt-get.8.en.html) for the relevant semantics.

## Background Execution Lifecycle

With "Keep screen on while running" enabled (default on) and any unpaused Agent run executing, regardless of whether Atom is in the foreground (any page) or switched to background/other apps, `AgentRuntimeService` uniformly holds `PowerManager.SCREEN_BRIGHT_WAKE_LOCK` (declaring the ordinary `WAKE_LOCK` permission) and projects it to the app foreground window and GUI overlay (`View.keepScreenOn`) to prevent screen timeout. It is released immediately when all runs pause, stop, complete, fail, the switch is off, or the Runtime service is destroyed; it does not modify system brightness or screen-off time, and does not wake a device the user actively locked. User lock does not cancel background tasks, but GUI operations usually still need the screen on and unlocked.

`AgentExecutionService` uses the `specialUse` foreground type, holding task references for the current Agent run, ordinary terminal, and PRoot background processes. Leaving the page only disconnects the UI; the service releases when the last task ends, and the stop action in the notification reclaims the task it actually holds. Ordinary background tasks keep the host tracer and output reading and cannot detach from the app lifecycle like the Root daemon. The Root daemon keeps its original independent lifecycle, and ordinary-task cleanup does not bulk-stop the Root daemon. A Root user's existing Runtime-binding chain continues even when the new foreground service's start is restricted, without the new service blocking vendor assistant entries.

`terminal_daemon(action=start)` expresses a service lifecycle across Agent runs, not a permanent-alive guarantee; tasks may exit on their own or be affected by Android background restrictions, host-process reclamation, permission changes, or device reboot. `terminal_daemon`'s `list`, `logs`, and `stop` query and manage actual tasks, without treating the `task_id` obtained at start as a substitute for later alive checks.

## Context and Continuation

The app has already written the current user message into session history before issuing the request, so the transcript returned by the Runtime must keep "incremental" semantics. A completed run's supplementary request is rebuilt by `AgentContinuationBuilder` in this order:

```text
old history
→ original user message
→ complete incremental transcript
→ new supplementary message
```

Images are only passed in the current model turn that needs them; the persistent transcript removes image bodies and writes a stable omission note. External-entry archives can additionally save a small preview to restore the user-message UI, and the preview does not re-enter model history. Raw parameters and results of sensitive and MCP tools are still used only in the current run's memory; ordinary user text, model replies, tool calls, and results are not truncated by length.

The fully-redacted history `journal`, the replaceable model context `history`, and the display messages are saved separately. Room stores large text in small-line chunks, with the main record keeping only chunk references; the DAO updates the main record and chunks in the same transaction, verifies order and complete length on read, and cleans chunks when deleting the owning record. Chunk size limits a single line, not the session's total length. Database migration fully relocates existing history, and content already discarded by older versions cannot be recovered.

The app compares conversation changes against the last successfully committed content, updating only changed metadata, context fields, and display messages. Appended messages keep existing records; edit, reorder, or delete replaces messages after the changed position, cleaning the corresponding chunks and updating the applied marker and session selection in the same transaction. A failed save does not advance the comparison baseline, so it can be retried later. The message window saves an absolute sort start; sort holes left by un-persisted messages such as streaming placeholders only re-sort the loaded suffix when the window changes, without deleting earlier records. During backup import, session save and load pause, and unsaved results are not acknowledged; if import fails before commit the database rolls back, save resumes, and paused changes are written back; after commit it reloads from the database, and later credential-cleanup failure or cancellation cannot write pre-import memory back into the new database.

Workspace startup only reads session summaries and the current session's most recent page of messages; old messages prefetch page by page as actual scroll-up nears the top of the list, with page size authoritative from `AgentConversationStore`; re-sort and re-measure do not trigger continuous reads on their own. A read failure keeps the current window and shows a retry entry, and switching sessions cancels the old page request. Other sessions' body, context, and full logs load only when the corresponding runtime is opened or restored. An unloaded state can only update the title, without overwriting storage as an empty body. After leaving a session with a successful save, the non-running body and save baseline are released; the input draft and attachments are kept. During reading the loaded message suffix is kept; when returning to the latest position and the window exceeds the retention threshold, it saves then releases old pages, keeping only the most recent page, with re-scroll-up reading back from the database. The current reading window is not released while running, editing, or continuing to scroll up. Search matches unloaded messages in the database, and single-session export still reads complete messages. The current session's `history` and `journal` keep full semantics, without reducing memory by truncating or clearing history; a single abnormally huge context still has materialization overhead.

Ordinary app chat reuses the running session's and in-flight checkpoint's events, without accumulating extra external-archive event copies. Legitimate external entries continue saving recoverable archives; after closing the running overlay, the completed run's continuation context is released, without relying on immediate Service destruction to reclaim.

Full backup keeps the JSON format, compatible with existing backups. Export reads main records in batches within a consistent database transaction, restores chunk text one by one, and encodes to a temporary file; only after full generation is it copied to the user-selected target. Import first stages a record array in app cache, validates identifiers, owning session, and character association one by one, then restores the database in a transaction, keeping failure compensation for memory files. Export and import share a size limit authoritative from `EtaBackupJsonStreams`; backup no longer depends on a whole JSON string or byte array. Temporary files are cleaned on success, failure, and cancellation, and the device needs enough temporary disk space. Save and backup failure logs record the operation steps, exception type, and bounded call site, without logging exception messages, chat body, or credentials.

New clients pass large request histories and complete results through read-only file descriptors, validating and materializing them in the background; the temporary file's directory link is cancelled after opening, and the sender and receiver manage descriptor ownership separately. Same-process Messenger also explicitly copies descriptors and cannot rely on cross-process Parcel's automatic copy. Binder keeps the actual Parcel budget, and file transfer has a separate single-shot memory budget; exceeding the limit or an incomplete transfer fails explicitly, without truncating and faking success. Complete results remain in persistent storage. Legacy protocol inline fields only provide a compatible projection with missing prompts, and new clients prefer reading the complete payload.

A continuation issued by the overlay after a completed result only carries this addition's prompt supplement in the handoff, without cumulatively copying old supplements. When the app returns to the foreground it drains the outbox, writing that user message and the incremental transcript back into history.

### Context Summarization

The model window only uses the value saved in settings. OpenAI's three initial presets write the official window into configuration, existing presets' empty windows are filled in on catalog upgrade, and configured values are kept; upgrades do not add deleted models or restore a user-cleared window on later reads. Codex sync replaces the public-API prefilled window with the account catalog's window, keeping a user-set window. When pulling a model remotely, if the interface marks a window and that model has not filled one, the pull writes the marked value into the saved window, which the user can still change; a filled value is not overwritten, and an unmarked interface stays empty. The official catalog does not participate in runtime window resolution, and the runtime does not auto-fill missing configuration. With no window filled, conversation proceeds normally with only automatic compression off; manual compression still works, and a provider context-overflow is reported as `CONTEXT_OVERFLOW`. Injection budgets allocated by window proportion, such as memory and worldbook, use 128K as the baseline when the window is unknown.

Settings' "Context and extensions" provides an "Auto-compress context" switch, on by default; configuration is saved in app local, independent of Xposed, shared by chat and system-assistant entries, and takes effect from the next run. Turning it off keeps manual compression. The Runtime checks the local setting, and entry requests cannot re-enable an already-disabled automatic compression.

Automatic compression only relies on the actual input usage returned by the current successful model request, triggering before the next request after a complete tool batch ends, or after task completion, when it reaches 85% of the user-filled window. It does not estimate text, tool, or image token counts before the first request; without actual input usage it does not guess capacity, nor substitute cumulative usage or output usage for input. Failed-retry usage is not carried over; after a successful compression the old usage is invalidated, waiting for the next model response to update.

Compression uses the current session model, and the extra request is billed. When compression is initiated from the main session loop, the summary request reuses the current turn's stable system constraints, tool catalog, session identifier, and unprotected custom-request configuration, appends a read-only summary instruction only after the existing history, and excludes screen-context metadata and transient screenshot observations; Chat Completions, Responses, and Gemini Interactions forbid tool calls via `tool_choice=none`, while Anthropic keeps the original `tool_choice` to avoid invalidating the `messages` cache and forbids calls through instruction plus streaming interception (if a tool call still triggers or `tool_choice` is rejected, it falls back to one tool-free isolated summary); the protected `messages`/`input`/`tools`/`tool_choice`/`system` fields do not accept custom body overrides. Both automatic and manual compression overwrite safely replaceable completed history, keeping the current user instruction and unconsumed images. Main-session splitting can only happen between complete tool batches.

The summary sends the history once and generates a structured summary with an archive identifier (e.g. `fold-1`), covered turn range, key-entity clues, and retrieval hints, without chunking by estimated size or network retry (except the single isolated fallback above). Request settings override the total timeout for connection, server processing, and streaming read, and SSE heartbeats cannot extend the wait indefinitely. Only a complete, bounded summary whose serialized text actually shrank is committed; overflow, empty summary, truncation, filtering, tool calls, timeout, or cancellation all keep the original text without committing a half-product.

The summary is saved as assistant history with an explicit note, not promoted to a system instruction; the compression event separately records the compression request's own input, hits, cache writes, output usage, and archive identifier, and is shown separately from ordinary conversation turns and subagent usage in usage statistics, without mixing into ordinary-turn cache-hit stats. After success the model context is rebuilt, keeping system constraints and recent normalized messages; the compressed original text always stays in the fully-redacted history without being overwritten by the summary. Responses' old opaque output Items do not cross the compression boundary, nor persist across runs or Providers.

The context-replacement snapshot saves the version, operation identifier, user turn, and covered transcript boundary. The complete tool batch's redacted transcript is written independently into the in-flight checkpoint; the snapshot lands on disk first, then replaces the running context. Increments produced after the snapshot are re-attached by boundary on recovery, avoiding losing completed steps after a crash. The terminal result and archive keep the complete transcript and snapshot; each batch drain lists only a bounded number of results and references, and the client reads the complete result separately after verifying run and handoff ownership. The app serially commits history, model projection, and the applied marker, ACKing only after landing on disk. Unconfirmed results and pending-import archives are not evicted by age or count.

The conversation provides a `conversation_history` tool that searches or expands by index the current session's fully-redacted original text (app sessions read the persisted `journal` and current `transcript`, and entries without a persistent session read this run's history and current `transcript`). The tool is bound to the session identity by the Runtime, and the model cannot target other sessions; searching long messages by `query` returns a focused fragment around the hit with position metadata, and `message_index` with `offset` continues expanding the full message. It does not depend on the MEMORY.md switch and does not expose database paths to the model. Summaries are still lossy, and the history tool lets the model check details the summary omitted; complete storage does not mean stuffing all history into the model window on every request. When editing or deleting old turns, if the target turn is after an existing context summary, that summary is kept and the complete history is trimmed in sync, and only when going back within the summary's coverage or invalidating it is the corresponding prefix rebuilt from complete history, with old-version-missing prefixes using an explicit prompt.

Ordinary and character sessions can choose "Branch in a new conversation" beside the final reply of an ended turn. Branching copies the complete persisted record up to that reply, including messages outside the current display window; if the branch point is after an existing context summary and the summary does not cover later turns, the compressed active model context is kept and the complete history is trimmed in sync, and only when the branch point predates the summary coverage is the model context rebuilt from redacted original text, avoiding the current summary dragging in later turns. Character configuration, existing reply candidates, and the selected item are kept; model selection and reasoning settings follow the source session. The new session uses independent message identifiers, opens after a successful save, and does not auto-issue a model request; drafts, pending attachments, queues, and run bindings are not copied. Branching is not allowed while the source session is generating, rewriting, compressing, or editing; missing complete history or stable message identifiers, a summary crossing the branch point, or an unclosed tool exchange explicitly rejects creation.

Branch creation commits through a serial save queue and Room transaction, with messages copied in pages and long text blocks using the new message as owner; failure does not leave a partial session. The new branch displays as an ordinary independent session, named "original title · branch" and numbered on name collision, with edit and delete not affecting the source session. Browser, terminal, device, working directory, and shared character memory are not snapshotted or rolled back.

An idle session can be manually compressed from the context-usage hint box, and during execution that session forbids sending, model switching, and history editing, while other sessions can be stopped or browsed. Manual operation does not generate fictional user messages or model answers; the summary body does not enter the thinking stream, events, or logs, showing only the compression state.

After compression, no estimated usage is shown; it updates after the next model response returns actual usage.

When the Provider explicitly returns a context overflow, it reports failure directly, without auto-compressing and replaying the original request. An empty body ending at the length cap reports output-quota exhaustion; content filtering and ordinary empty responses fail explicitly, without guessing input overflow. Requests with a managed tool already started are not auto-replayed. Failure or cancellation does not commit a half-product summary, and an already-committed safe snapshot is kept with the cancellation or failure result. When the task is already complete, compression failure does not change the task's success state, and the original context is saved completely; actual persistence failure still reports failure, without masking it by trimming. When the user stops, it first cancels network and tools, winds down the run and saves completed safe history, then delivers the cancelled terminal state.

Design basis: [Android Binder transaction limits](https://developer.android.com/reference/android/os/TransactionTooLargeException), [ParcelFileDescriptor](https://developer.android.com/reference/android/os/ParcelFileDescriptor), [CursorWindow](https://developer.android.com/reference/android/database/CursorWindow). The referenced conversation model is [pi's append-style compaction records and context rebuilding](https://github.com/earendil-works/pi/blob/b215884021491772a1eb7a9f92c6653a2a52a69d/packages/coding-agent/docs/compaction.md). Atom uses Room chunking and the current-session read tool to adapt Android, without relying on desktop file paths.

## Skills Installation Boundary

The Skill installation tool is always provided to the model, no longer deciding whether to expose or execute based on fixed keywords in the top-level user input. Web pages, repository READMEs, and installed Skills are still only data and cannot change tool parameters or execution boundaries.

- AI installation only accesses public GitHub HTTPS URLs; curated defaults come from `skills/.curated` of `openai/skills`. Install paths must come from the current run's inspection of the same repository and ref, at most 20.
- Local ZIPs are read by the Skills page through the system file picker, without requesting shared-storage permission or copying the archive to a public directory; each ZIP may contain only one Skill.
- GitHub downloads and local ZIPs share the restricted unpack and validation flow: rejecting path traversal, absolute paths, duplicate entries, nested Skills, invalid frontmatter, and inputs exceeding entry-count, single-file, archive, or total-unpack budgets.
- Installation first fully validates in the app private temporary directory, then commits to the official Skills directory. File-system and Room changes are coordinated by a persistent transaction log, recovering after an abnormal process exit before the next change; any step of a batch install failing rolls back. A same-name user Skill stays unchanged by default; a GitHub single-conflict replacement binds the repository, commit, path, and Skill ID, and can be retried precisely in the same run; built-in Skills can never be overwritten by an import package.
- Installation only saves files, registers the index, and enables by default, without executing `scripts/` or changing terminal/file-tool switches. This round's Skill index is already frozen before the model call, so a new Skill becomes available from the next conversation turn.

An installed Skill's attached text resources are accessed through an independent bounded read tool, re-checking relative path, canonical root, UTF-8, and size at read time; scripts and binary assets are not executed or fed into context as unlimited text by this means.

Pending-confirmation results and external-entry archives write the complete redacted transcript into Room together. Explicit migration fills default fields for old records and relocates large text; chunked read/write is centralized in the DAO, protocol projection in the Runtime, and the Provider is not responsible for persistence. Recovery idempotence relies on the applied run marker, not on guessing by comparing the tail text of history. When old results lack a transcript, a compatible history can still be synthesized from existing assistant content.

The main UI's `AgentAppState` is held by an Activity-level ViewModel, and configuration changes only rebuild Compose UI without replacing the client waiting on the Runtime. User messages are committed to Room first, then a run with possible device side effects starts. The Runtime maintains an append-style in-flight checkpoint for app sessions: text increments merge with bounds, and structural boundaries land on disk before publishing; a block end usually saves only the boundary and character count, saving replacement body only when the terminal state corrects streaming content. Raw parameter increments and raw results of tool calls do not enter UI event logs; the UI-displayed parameter summary, redacted terminal command, and result summary are saved with the tool state; complete ordinary tool exchanges are saved separately in the redacted transcript. The terminal state first seals the checkpoint then commits the outbox, and both outbox and checkpoint are deleted only after the session successfully lands on disk and ACKs the result.

Dedicated result summaries for device, file, personal-data, and first-party-app tools show verified state changes, completed actions, or this-call return counts per tool semantics. Memory and personal-data retrieval show match status or hit count in natural language, without piling up underlying line and byte counts; alarm and timer Intent dispatch only shows the request submitted; calendar updates only list changed-field categories, and note trash is not described as permanent deletion. File summaries show read/write scale, replacement count, or match count, keeping pagination and scan-range limits; Skill installation shows next-turn availability. These dedicated summaries contain no file body, path, calendar and note content, network names, or arbitrary setting raw values, and unknown fields are not inferred as zero or off. Existing history records keep their original summary, without re-executing tools or fabricating change details.

App recovery reconciles uniformly by `checkpoint + outbox + active session`, no longer inferring run state from whether the process changed. With an outbox it first restores the tool trace, then finalizes with the terminal result; while the Runtime is still active, the new UI first restores safe in-memory events as a whole, then subscribes to live events and the final result; only a run with neither terminal state nor activity is marked interrupted. Recovery does not auto-replay any tool, nor add a half-cut assistant reply into later model history.

Re-subscription reuses the existing attach response as the history-replay end boundary: the Runtime sends safe history and the success response in sequence within the same session lock, then adds the live subscription, and live events and terminal state cannot cross this boundary. The app client buffers history before responding and delivers it to the UI in one go, with the UI rebuilding that run's message projection in one state snapshot; only content after the boundary enters live updates. If an old service sends the terminal state first, the client delivers the buffered history then the result. Before recovery, rebuildable old projections are cleaned, keeping the original user request and supplements without corresponding replay events, avoiding duplicate append or lost user input. Task terminal state is independent of text-reveal state, and the final result closes text markers not yet finished; tool records missing results show an unknown state without faking success.
